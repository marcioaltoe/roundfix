# 2026-08-04 — The documented sandbox escape does not exist on the Codex adapter

status: pending

## What was observed

A QA gate recorded ten rows as `blocked (environment)` because the Agent sandbox
denied TCP to the local PostgreSQL:

> `rtk make verify` exited 2 … Every failure was in
> `packages/backend/test/postgres.integration.test.ts` and had the same sandbox
> boundary: `connect EPERM` to `::1:8433` and `127.0.0.1:8433`. … The unblock
> action is to rerun `rtk make verify` in a full-access session that permits TCP
> connections to the configured local PostgreSQL on port 8433.

That unblock action is also what
[QA gate round economics](2026-07-29-qa-gate-round-economics.md) names as the
remedy — *"The only documented escape is `--agent-full-access`"*.

Following it fails. The Run died ten seconds after start, before QA began:

```
roundfix: implement failed after Run start: run Agent for run "…" QA step:
set acpx Agent Session mode "full-access": acpx infrastructure error after exit code 1

--- acpx stderr tail ---
Agent rejected session/set_mode for mode "full-access": Invalid params (ACP -32602).
The adapter may not implement session/set_mode, or the requested value is not supported.
```

The default backend runtime — `codex / gpt-5.6-sol`, the preferred selection for
`general`, `backend`, `qa`, and `review` — does not implement `session/set_mode`.
So the only documented escape from the sandbox is unavailable on the adapter that
runs almost every Roundfix Agent.

The block turned out to be avoidable for another reason: on a later Run the gate
provisioned its own disposable PostgreSQL (`oraculum_qa_*` databases) and closed
with `rows_blocked_environment: 0`. The sandbox never needed relaxing. That is
the good outcome — and it makes the advertised flag pure downside: it cost a Run,
and a Supervisor that trusted it would keep paying.

## Root cause

Three layers disagree about a capability none of them verifies:

1. `implement`, `resolve`, and `watch` all accept `--agent-full-access` with no
   adapter capability check. The flag is validated as a flag, not as something
   the selected runtime can honour.
2. `doctor` and `profiles validate` prove runtime/model/reasoning tuples through
   disposable sessions, but never probe `session/set_mode`. A green `profiles:`
   line says nothing about mode support.
3. The failure surfaces only *after* Run creation, as an `acpx infrastructure
   error` during the first Agent step — past the point where a Run exists,
   a worktree was created, and bootstrap ran.

Meanwhile the QA gate's own report recommends the flag by name, so the advice
that reaches a Supervisor is generated by a component that also cannot check it.

## What would settle it

- Reject `--agent-full-access` at Preflight when the resolved runtime does not
  advertise `session/set_mode`, with the same shape used for a rejected model:
  name the runtime, the unsupported capability, and the alternative. Exit `2`
  before Run creation instead of failing a live Run.
- Add mode support to the `doctor` proof, so `--agent-full-access` availability
  is visible before anyone plans around it.
- Fix the guidance the gate emits. Recommending a documented escape that does
  not work on the default adapter converts one blocked gate into two.
- Prefer the mechanism that already worked: gate-provisioned disposable
  infrastructure. If the QA category can provision its own PostgreSQL, that
  should be the documented answer to a sandbox-denied dependency, and the
  earlier finding's per-category capability grant should be scoped against it.
