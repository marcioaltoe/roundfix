# Agent selection profiles — generated defaults block Vortex runs (2026-07-17)

Vortex dogfooding used a Project Config generated by `roundfix setup`.
Preflight correctly created no Run, but it exposed a legacy adapter override,
unproven generated defaults, and canonical invocation guidance that bypassed
category profiles.

## 1. Generated GPT-5.6 defaults fail disposable-session proof

- **Symptom / evidence**: `roundfix profiles validate --json` exits `2` for
  `codex / gpt-5.6-sol / high`. The adapter rejects
  `session/set_config_option` for `reasoning_effort=high` with ACP `-32602`.
  Earlier proof also showed that `gpt-5.6-terra / max`, which `roundfix setup`
  generated as the fallback, is not advertised by the installed adapter.
- **Environment**: macOS Apple Silicon; Codex CLI `0.144.5`; ACPX `0.12.0`;
  legacy `@zed-industries/codex-acp` `0.16.0`; official
  `@agentclientprotocol/codex-acp` `1.1.4`.
- **Corrected root cause**: `roundfix setup` wrote a bare `codex-acp` ACPX
  override after finding an executable on PATH. That executable resolved to the
  legacy Zed adapter and masked ACPX `0.12.0`'s current built-in command,
  `npx -y @agentclientprotocol/codex-acp`. The legacy adapter advertised Sol
  without an independent reasoning control and omitted Terra/Luna. The
  generated configuration was never proven against the effective adapter
  identity and exact tuple before it became the default.
- **Corrected runtime evidence**: a disposable session using the official
  adapter `1.1.4` advertised Sol, Terra, Luna, GPT-5.5, and independent
  reasoning values including `high` and `xhigh`. It accepted and reported
  `gpt-5.6-sol / high`, then closed successfully without an Agent prompt.
- **Action / suggestion**: verify and provision the supported official adapter
  before generating config, then prove every exact runtime/model/reasoning
  tuple through live advertised ACP capabilities. Keep Sol/high as Preferred
  and GPT-5.5/xhigh as the required generated fallback. Do not substitute
  model-managed reasoning for an explicit `high` request.

## 2. Canonical `--agent codex` guidance masks category profiles

- **Symptom / evidence**: after replacing the fallback with
  `gpt-5.5 / xhigh`, this command exits `2` before Run creation because the
  resulting Preferred Selection duplicates the fallback:

  ```text
  roundfix implement --spec 0006-uniformidade-uuidv7 --agent codex --qa --detach
  ```

  Review Run `run_20260717T142229Z_194a8e725fb8e7e6` independently confirmed
  the selection behavior. The Project Config preferred
  `gpt-5.6-sol / high` for `review`, but `resolve --agent codex` ran with
  `gpt-5.5 / xhigh`.
- **Root cause**: `invocationProfileOverride` treats `--agent` by itself as a
  complete one-Run Preferred Selection override. The canonical Roundfix Skill,
  CLI usage, and user guide always include `--agent`, even though those same
  documents say omitted invocation flags use the category profile. The normal
  documented command therefore bypasses the profile-driven default.
- **Action / suggestion**: make profile-driven commands omit `--agent` unless
  the caller deliberately requests a complete one-Run override. Update CLI
  usage, the canonical skill, and examples together. Preflight must explain
  that an agent-only override selected the legacy tuple and either reject it
  with an exact remediation or define a non-duplicating runtime-only semantic.

## 3. Doctor does not prove the effective Agent Selection Profiles

- **Symptom / evidence**: `roundfix doctor` reports
  `model: ok (gpt-5.5)` while the effective Vortex profiles contain
  `gpt-5.6-sol / high` and `gpt-5.5 / xhigh`; the subsequent operational
  preflight fails the first profile tuple.
- **Root cause**: Doctor probes the legacy Codex runtime default instead of the
  effective required profiles and their configured fallbacks.
- **Action / suggestion**: Doctor readiness must use the same effective-profile
  resolution and disposable-session proof boundary as operational preflight,
  or explicitly report that profile readiness was not checked. Route this into
  `docs/specs/0036-doctor-skill-readiness` before the CLI claims the repository
  is ready.

## 4. A required distinct fallback can leave no configurable profile

- **Symptom / evidence**: `roundfix profiles configure --scope project` first
  rejected a `review` profile without a fallback. A second attempt used
  `codex / gpt-5.5 / xhigh` as both the Preferred Selection and fallback; the
  command rejected the duplicate selection and left the Project Config
  unchanged again.
- **Root cause**: the profile contract requires a non-empty Fallback Chain and
  rejects a fallback identical to the Preferred Selection. Both rules are
  correct, but together they make configuration impossible when the user has
  authorized and proven only one tuple. At the time of this attempt, no second
  distinct selection had been both authorized and proven for the profile.
- **Action / suggestion**: preserve the required-fallback and tuple-uniqueness
  rules. When no distinct proven fallback is available, the configurator must
  say so directly and identify the next proof or authorization needed. It can
  present Sol/high only after official-adapter and exact runtime proof; it must
  not silently choose another model, duplicate the Preferred Selection, or
  convert explicit reasoning to model-managed behavior.

## What worked — keep

- Preflight stopped before Run persistence, Agent work, worktree creation, or
  file changes.
- The structured profile validation output named the rejected tuple, affected
  categories, ACP error code, and model-managed recovery option.
- Profile configuration rejected both a missing fallback and a duplicate
  preferred/fallback tuple without changing the Project Config.
