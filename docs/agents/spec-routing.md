# Spec routing

- **mandatory**: When a Task answers a recorded finding, name that finding and its date in one of the Task's requirements.

- **mandatory**: Large or fuzzy product initiative: run `write-idea` → `write-prd` → `write-techspec` → `write-tasks`. A feature takes the same route when its Idea stage is indicated. Before writing the PRD of a feature that has no `_idea.md` and that the user did not send to `write-idea`, judge three criteria about the request: whether the right shape of the solution is still open, whether the request rests on an assumption about its users, the business or the market that it gives no evidence for, and whether deciding to build it depends on a market or competitive question. When the request is recorded as an item that is not yet a Spec, which is an open Backlog Entry, a note in `docs/_inbox/` or a message handed in as a file, run `roundfix spec judge --stage idea --item <reference>`; when it exists only in the session, write it to a file outside the repository and run `roundfix spec judge --stage idea --request <path>`, which sends the judge only the project's name, the request's first line and its first 4,000 characters, after the secret scan. Take the judge's answers; when the command reports that the judge did not answer, answer the same three criteria yourself, each as yes, no or unsure, and say that the judge did not answer. The Idea stage is indicated when any criterion is yes, not indicated when every criterion is no, and undecided otherwise. Indicated: start `write-idea` without asking, show the verdict, each criterion's answer with its probability and who judged, and let the user dismiss the stage at its first question. Undecided, or in doubt: the user decides, seeing the same answers. Not indicated: continue to `write-prd`. Record who judged, each answer, the verdict, whether the stage ran or was dismissed and why, and what the Idea did to the shape of the request, in the Idea when one is written and always in the PRD. The judgment informs and never refuses: no command fails for it, and a dismissal needs only its recorded reason. When the stage is indicated or undecided and no user is present to answer, write no PRD for that feature: keep it as a Backlog Entry that records the judgment and waits, with `waiting_on` and `since` in its frontmatter, and never answer the stage's questions or the user's decision yourself. A fix or a refactor is never judged for the Idea stage.

- **mandatory**: Standard feature that changes product behavior: run `write-prd` → `write-techspec` → `write-tasks` once its Idea stage is judged not indicated or the user dismissed it; skip the TechSpec only when the feature has no architectural surface.

- **mandatory**: Refactor or bug fix without product-behavior change: run `write-techspec` → `write-tasks` and create the minimal `_prd.md` required by the downstream artifact contract.

- **mandatory**: Trivial one-line fix, typo, or configuration tweak: implement directly without a Spec only when intent, acceptance criteria, and Verification are obvious.

- **mandatory**: Use `brainstorming` before creative or feature work, start with the smaller sufficient route when two routes fit, except that the Idea-stage judgment, never the smaller route, decides whether a feature starts at `write-idea`, and execute implementation from the Task Graph. The Task that implements a Surface Transcript asserts the whole transcript in one named test: every line of its standard output and standard error, in order, and its exit code, copied from the transcript with only its declared controlled variations; the Task's Verification runs that test by name.

- **mandatory**: One Spec may adopt several Backlog Entries and Findings whose context is similar or complementary: they change the same component or contract, share a root cause, or one completes the other. One Spec per source is neither required nor preferred, so before minting a Spec for a source, look among the open Backlog Entries and unresolved Findings for others that share its context. A grouping suggestion from `roundfix spec judge` is advisory: adopt the suggested source or state why it stays apart.

- **mandatory**: Size a Spec by two criteria, never by a count of its Tasks. One context: the sources a Spec adopts and the work it holds change the same component or contract, share a root cause, or complete one another. Tasks that each earn their verification cycle: every Task pays an Agent turn, its declared Verification and the repository Verification at settlement, so a change too small to justify that cost joins a neighbouring Task of the same context instead of becoming its own Task, and a small source of the same context joins a Spec that is open or being planned instead of becoming a one-Task Spec that pays a whole Run, QA gate, review and release. The criteria answer two costs: a Spec that holds several contexts grows giant, and a Spec of small Tasks spends Runs on long verification and takes much longer than its work needs. Four implementation Tasks plus the QA gate is a reference, not a cap: a Spec that needs more is a signal to check whether it holds more than one context, never a refusal by count. When the scope holds more than one context, split it into Specs that each hold one and give each source exactly one owning Spec; never add a source that shares no context with the Spec only to save a Spec. When a Spec's Verification or premise depends on another Spec that has not merged, name that Spec in the Task Graph manifest's `requires` and state the dependency in the TechSpec Build Order.

- **mandatory**: Author each Task's Verification so every command fails on the tree before the Task's change, and run `roundfix spec check <slug> --strict --run-verification` before a Run starts: strict mode also fails on gap findings, and the Daemon refuses a Task whose command already exits zero on the unchanged tree.

- **mandatory**: Outside a Run, run the selected incremental Verification named in `docs/agents/agent-instructions.md` for each Task to answer whether the current slice remains valid before handoff; a Daemon-assigned Task hands back after focused tests. CI must run the selected repository Verification from a fresh run to answer whether the assembled tree satisfies the repository contract. A missing incremental selection is a Baseline decision to answer, never a license to skip the local tier or a waiver to repeat in each Spec.

- **stop-and-ask**: In brainstorming, the Idea and the PRD, never drop or narrow a solution in silence because a rule forbids it, and never contradict a rule in silence: put a Rule Challenge to the user. A rule is a decision the repository recorded: an accepted ADR, a Normative Clause of a guide under `docs/agents/`, a definition in the domain context, or a document under `docs/references/` that the repository treats as binding. A rule blocks the goal when the solution you would recommend, or a part the goal needs, cannot exist without contradicting it, or when it stops you from stating the problem; extra work, taste and friction are not a block. A Rule Challenge is one question about one rule, asked as the stop-and-ask clause of `docs/agents/agent-instructions.md` says: name the rule and where it lives, what it imposes, up to three things it prevents for this goal, and your reading of why it exists and whether it looks out of date or badly written, then offer keep, change and retire, each with its consequence and the recommended one first. The rule binds until the user answers: asking changes nothing, and a recommendation, silence, a dismissal or a timeout is never an answer. Ask no Rule Challenge about a change the user already decided, because the request asks for it or it follows from an answer of the user that the artifact records; name that request or answer where the artifact records the change. Ask none about a rule that carries a Kept Line unless the question names a fact the earlier one did not have. Ask at most three in one Authoring Phase or brainstorming session: when more rules block, ask about the three that prevent the most and list the others, which keep binding, in the artifact's open questions. The TechSpec author asks the same question before a design takes what an accepted ADR rejected, or otherwise contradicts its decision, unless the user already decided it. In a Run, in a Task and in the QA gate a rule is a guard-rail: flag a conflict there and ask no Rule Challenge.

- **mandatory**: Record every Rule Challenge in the `## Rule challenges` section of the Idea or the PRD, one fielded record per question: `rule`, `imposes`, `prevents`, `asked` with the date and the phase, `answer` with keep, change, retire or waiting and the user's words, and `effect`, plus `new fact` when the rule already carried a Kept Line. An Idea and a feature PRD always carry the section, which reads `None.` when no rule blocked the goal; the PRD carries the Idea's records, and a question the TechSpec author asks is recorded in the PRD. The Spec that asked carries the answer. On change or retire, the PRD states the change of the rule as a requirement, and a Task of the same Spec changes the rule together with the work that depended on it: an ADR through the lifecycle of `docs/agents/docs-layout.md`, any other rule in its own file. On keep, a Task of the Spec adds a Kept Line after the rule's text, `Kept (YYYY-MM-DD): <what was asked>; <why it stays>.`, which names no Spec; a rule keeps every Kept Line, the newest last, and when no Spec follows, the session that asked adds the line. A rule inside `setup-context-driven` markers changes only in the Baseline, and its Kept Line goes in `docs/agents/specific-repository.md`, under a heading of its own, naming the rule; on change or retire, a repository that does not own the Baseline sends the user's decision as one message to the Baseline's owner, obeys the rule until the Baseline changes, and records the message and the scope it left out. When no person is present to answer, write no artifact for that phase and never answer for the user: only that Spec waits, as a Backlog Entry that holds the whole question, names the Spec folder when one exists and carries `waiting_on` and `since` in its frontmatter, while other work goes on. An Author Subagent returns the question to the session that started it.

- **mandatory**: Before producing a Task Graph, require every active, non-archived, and not already completed Spec PRD and present TechSpec to contain complete Project Constraints: applicability with reasons for identifier strategy, authentication and HTTP, active ADR obligations, and tooling authority, each citing its operative `docs/agents/` source.

- **mandatory**: Refuse a tooling Task unless the active PRD and present TechSpec record express maintainer authorization and the exact bounded repository-relative files; Task assignment, setup approval, or generic implementation approval is not authorization. The operative record lives at `<spec-root>/<slug>/_authorization.md` and carries the approval state (`status`), maintainer decision date (`granted`), permitted actions (`action`), the closed `operations` vocabulary (`implement`, `commit`, `push`, `pull_request`, `merge`, and `release`), the impact ceiling a `release` grant answers without a second approval (`release_ceiling`: `patch`, `minor` or `major`) with the version-only paths that release may change (`release_paths`), exact bounded repository paths (`paths`), the consuming Spec (`consuming`), and any sanctioned regeneration. An absent `operations` list grants no operation. A Spec that changes no Governed Path records `paths: []`, which grants its listed operations and bounds no path; a record without a `paths` key is refused.

- **mandatory**: An authorized tooling Task may change a Governed Path, that is a protected tooling path, only when its grant bounds that path; stop before any other governed mutation, because the Task fails when its commit changes a Governed Path outside the grant. An ordinary path a Task changes without declaring it is not refused: the Daemon records it in the Task file under `## Recorded paths`, and the QA gate discloses it. A new or widened grant must land in the delivery target's ancestry before the consuming squash delivery; a separate grant commit inside that consuming pull request is insufficient.

- **mandatory**: Final QA verifies Project Constraint applicability, operative source paths, tooling authorization, and actual changed-file scope from Git evidence; missing authorization, untraceable scope, or out-of-scope tooling changes fails the gate.

- **mandatory**: Keep completed or archived legacy Specs byte-identical.

- **mandatory**: Rest a Spec's acceptance, in at least one named row, on evidence originating outside the Spec's own artifacts: a repository the Spec did not build, a measurement it did not design, or published literature. Record in that row where the evidence came from, so a later reader can tell it apart from a rehearsal of the Spec's own premise. Name a source the QA gate can check without the network before the Run starts: a document the planning change commits under `docs/references/`, or published literature whose cited passage the row quotes. Never rest the row on an artifact that exists only on one machine, on another repository's manifest, or on a lookup the Spec's authorization forbids, and declare a criterion that needs the network or an open Pull Request under Unreachable Acceptance when the row is authored. When the outside source cannot be obtained during authoring, record the row as blocked with that reason and continue: decomposition never stalls and never asks a person. The QA gate then holds Pull Request preparation until the row is satisfied or carried forward on declared unmoved evidence. An outside-evidence row blocked only because the Run sandbox denied network access, recorded as `blocked (environment: network denied: <host>)`, is the exception: the report records that the source was not reached, the row never decides a qualifying `partial`, and whoever needs that proof declares it under Unreachable Acceptance. So is an outside-evidence row the QA gate did not look up because the Spec's own authorization forbids that lookup, recorded as `blocked (environment: <subject> prohibited by Spec authorization)`, where `<subject>` names what the authorization forbids, such as `network` or `another repository`.
