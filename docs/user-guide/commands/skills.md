### skills

```bash
roundfix skills list
roundfix skills check
roundfix skills install [--target project|codex|claude|opencode|all] [--dir <path>]
```

The binary ships 12 Roundfix-owned skills: the operational `roundfix` skill
plus the authorial workflow skills (`write-idea`, `write-prd`,
`write-techspec`, `write-tasks`, `setup-context-driven`, `implement-task`,
`brainstorming`, `business-analyst`,
`archive-spec`, `qa-gate`, `evidence-gate`). `skills list` also prints
recommended external skills, which install through your own tooling and are
never shipped. By default `skills install` writes to `<repo>/.agents/skills`;
`--target` selects user-scoped Agent skill directories instead.

Inside an adopted Git repository, `skills check` also inspects the skills the
repository's Baseline requires and fails with exit `1` for each Missing
Required Skill, printing
`.agents/skills/<name>: required by the Baseline and not installed; restore with roundfix baseline skills restore --profile <id> --skill <name>`
on stderr. Outside a Git repository, or without a Setup Manifest, it skips
Baseline skill inspection and still checks the shipped bundle.

When the bundle and repository checks pass, including an unversioned result,
`skills check` reads the Authoring Model Declaration from Project Config at
the repository root. On stderr, after the result and before the user-level
warning, it reports installed files that do not match:

```text
roundfix: warning: the installed files do not match the Authoring Model Declaration (skills.authoring.claude):
  <problem>
  next: roundfix skills install --target project
```

Each problem gets its own line. Problems appear in this order:

1. For each declared phase, in `idea`, `prd`, `techspec`, `tasks` order:
   `<skill> header is not the declared one` when an existing installed
   `SKILL.md` has a different top-level `model` or `effort`; then
   `.claude/skills/<skill> does not lead to .agents/skills/<skill>, so Claude Code does not load the declared header; link it there`
   when the two paths do not resolve to the same directory. A copied folder,
   a missing path and a dangling link all get the link problem.
2. For each declared entry, with `research` last: `<path> is missing`,
   `<path> differs from the declaration` for a changed Roundfix-generated
   file, or `<path> exists and was not generated by Roundfix; installation will not overwrite it, so move or rename it`
   for a conflict. Installation will not overwrite a file it did not
   generate; move or rename that file yourself.
3. For generated names without an entry, in the same order:
   `<path> has no declared entry` for Roundfix's leftover files, or the same
   conflict text for a file Roundfix did not generate while at least one
   key is declared. With no declaration, an unmarked file is not a problem.

The `next:` line appears only when installation can repair at least one
problem: a header, a missing or different generated file, or a leftover
Roundfix-generated file. Installation does not fix links or conflicts.
A missing installed `SKILL.md` adds no header problem. Header values compare
as parsed YAML, so quoting a value does not change the result.

If configuration cannot be loaded, the declaration warning is only:

```text
roundfix: warning: Authoring Model Declaration not read: <error>
```

The check prints none of the configuration loader's own warnings. A failed
skill check prints no declaration warning. All declaration checks only read
files and never change the exit code. Without a declaration or a leftover
generated file they add no output.

It also names each **Stale User Skill Copy**, a user-level Roundfix skill copy older than the binary, which an Agent harness can load in place of the project copy. It reads the copies from these directories, in order: `$CLAUDE_HOME/skills` or `~/.claude/skills`, `$CODEX_HOME/skills` or `~/.codex/skills`, `$OPENCODE_HOME/skills` or `~/.opencode/skills`, `~/.agents/skills` and `~/.config/opencode/skills`. Symbolic links are followed; when several links reach one folder, that folder is named once under the first directory. A copy at or above the binary's version, one without a comparable version and an unreadable one are not named. Nothing is written, and the exit code does not change.

```text
roundfix: warning: user-level Roundfix skill copies older than this binary; an Agent harness may load them in place of the project copy:
  <skill> <found> (binary <version>) at <path>[ -> <link target>]
  refresh: <command>
```

Refresh the first three directories with `roundfix skills install --target <claude|codex|opencode>`, `~/.agents/skills` with `roundfix skills install --target codex --dir <path>`, and `~/.config/opencode/skills` with `roundfix skills install --target opencode --dir <path>`. A refresh writes through a link to the folder the ` -> <link target>` names.

For `--target project` without `--dir`, installation loads Project Config
from the repository root and applies its
[Authoring Model Declaration](../configuration.md#authoring-models).
Configuration warnings go to stderr. A configuration error stops installation
before any write, prints `roundfix: skills install failed: <error>` on stderr
and exits `2`.

For each declared phase, installation adds `model` and `effort` to the
installed skill's frontmatter and writes its Author Subagent under
`.claude/agents/`; a research entry writes `roundfix-researcher.md` there.
It prints these lines on stdout after `Installed Roundfix skill for project:`
and before any lock lines, headers first, then generated files, then removals,
in phase order (`idea`, `prd`, `techspec`, `tasks`, then `research`):

```text
Applied declared header: <skill> (model <model>, effort <effort>)
Generated subagent: <path>
Removed generated subagent: <path>
```

The parenthesis includes only declared values: `model <model>`,
`effort <effort>` or both. `<path>` is repository-relative.

Before writing any skill, installation checks all five generated filenames.
Only a regular file whose first non-blank body line is its own key's
`<!-- roundfix:generated skills.authoring.claude.<key> -->` marker can be
overwritten or removed. With a declaration, any other file at one of those
names refuses the entire installation, with exit `2` and this stderr line:

```text
roundfix: skills install failed: <path> exists and was not generated by Roundfix; move or rename it, then run roundfix skills install --target project again
```

When a phase's installed skill held a top-level `model` or `effort` without a
declared entry, installation names it once on stderr when replacing it
with the shipped skill:

```text
roundfix: notice: .agents/skills/<skill>/SKILL.md held model or effort lines that no declaration covers; declare skills.authoring.claude.<key> in .roundfixrc.yml to keep them
```

Installation deletes only marked files at the five generated names whose
entries are no longer declared. With no declaration it writes the bundle
unchanged, refuses no unmarked file and removes only its own leftover
subagents. Other files under `.claude/agents/` stay as they are. Repeating an
installation with the same declaration changes no bytes or file modes.
A user-level target and any `--dir` target receive no declared header and no
generated subagent, and do not load the declaration.

After bundle installation, an existing `skills-lock.json` entry naming an
owned skill receives the installed folder's `computedHash` and loses its
`ref`; every other field is preserved. No entry or lock is created when no
matching lock entry exists. Each name whose hash changed is reported as
`Updated skills-lock.json computedHash: <name>`, followed by
`Removed skills-lock.json ref: <name>` for each entry whose `ref` was removed.

Roundfix reads a `skills-lock.json` of version 1 or 2, the version the skills CLI 1.8 writes; every `computedHash` it writes into the lock or compares with an installed folder follows the hash algorithm of the version the file declares, and it never changes that version.
