# Handoff — after the 0.3.1 release

Read `docs/workflow/spec-queue.md` for the ordered list; it carries the
reasoning per Spec. This document records what shipped on 2026-08-03, what the
session learned, and what is waiting on a decision.

## Where things stand

**Released: 0.3.1**, published to npm across all six coordinates through
Trusted Publishing with no token fallback. That closed the fallback window
Spec 0058 opened — `NPM_TRUSTED_PUBLISHING_FALLBACK` has been removed, so the
workflow's `FALLBACK_WINDOW` no longer matches `"1"` and the token path is
shut by construction.

The launcher was at 0.0.2 while the platform packages carried 0.3.0 from an
earlier versioning era; 0.3.1 is the first version above every published
coordinate and the first consistent release across all six. The `v0.0.3` tag,
which never published, was deleted.

**Archived this session:** 0071 (verification cost), 0072 (the authored QA
gate), 0074 (git spawn economy), and 0063 (superseded by 0070 without
implementation). All three implemented Specs closed under `qa_override`, each
with its rationale recorded in the Spec.

**Active:** ten Specs, none started — all are PRD plus TechSpec only.
`main` is clean, no worktrees, no open Pull Requests.

## What the loop can do now that it could not this morning

- **The QA gate is authored into the Task Graph.** `--qa` no longer exists.
  A Spec declares `qa: task_NN` naming a terminal `type: qa` Task, or
  `qa: declined` with a reason. Appending work after a gate reported
  invalidates that result at the next load, naming the insertion. Graphs
  authored before the contract keep working.
- **The local gate is incremental.** `make verify` costs about 5 seconds on an
  unchanged tree against 142 before. Editing one package pays that package.
- **CI runs the suite before a merge.** `ci-verify.yml` did not exist this
  morning; nothing ran tests on a Pull Request.
- **Per-Task verification proves the Task's effect**, in seconds rather than
  by running a whole package suite.

## What the session learned, in order of what it cost

1. **Artifact contradictions are the most expensive defect class.** Spec
   0072's close burned four gate executions on F-001: a PRD citing a tooling
   authorization it was not listed in. Reading two files catches it. This is
   why 0064 now leads the queue.
2. **One finding can suppress every row.** That same F-001 marked fifteen of
   twenty-four rows blocked, including every journey the Spec existed to
   prove. Four cycles reported the same fifteen. 0070 owns this, and absorbed
   0063's live features for it.
3. **Run residue is reclaimed by hand.** Branches and worktrees were removed
   manually at least six times, and Branch Integrity Preflight refused two
   commands until they were. 0068 and 0066 own this.
4. **Wait for the reviewer's decision on the exact current head before
   launching a gate.** Every resolve push creates the next review round, so a
   gate launched too early fails on threads the reviewer has not finished
   opening. Recorded in
   `docs/findings/_archived/2026-08-03-gate-and-review-rounds-need-a-convergence-rule.md`.
5. **Parallelising surfaces real defects, and that is the point.** Making 668
   tests parallel exposed a cancelled Run still starting a Verification child,
   process-global state in the detached-child path, and load-sensitive wait
   budgets in three packages. All fixed at the root. The rule held: a test
   that fails under parallel execution found shared state.
6. **Measure before optimizing — the instinct was wrong twice.** Cold-cache
   compilation was worth nine seconds, not two minutes. Deleting the twelve
   heaviest tests buys seven to fourteen seconds, not minutes. The suite was
   spawn-bound, not compute-bound: 36% CPU utilization, kernel time three
   times user, 13,926 git spawns per run.
7. **Removing spawns did not move the suite's wall clock.** Spec 0074 cut
   1,571 git spawns (13%) and the fresh suite stayed at 71–79 seconds, because
   a CPU-saturated suite hands freed capacity to another test. The reduction
   is real value for Runs against user repositories, which was always the
   larger half. The under-60-second target was not reached, and the Spec's
   report says so plainly.

## Traps this session hit, so the next one does not

- **The release version lives in `dist/npm/roundfix/package.json`**, not in
  `internal/app/version.go`. The workflow validates the tag against the
  manifest. Bumping only the constant fails at the first step. A test now
  asserts the two match — it fails red in the suite instead of red in a
  release.
- **The Task Graph is read from the commit, not the working tree.** A Spec's
  `_tasks.md` must be merged before `roundfix implement` can see it.
- **A Run's work stays on its Run Branch until integrated.** After a Run,
  `git merge --ff-only roundfix/run-<id>` — cherry-picking only the QA report
  silently leaves every Task commit behind.
- **`make verify` failing on a Pull Request does not block its merge**, because
  `main` has no branch protection at all. That is how PR #88 merged red and
  broke `main` for one commit. See "Waiting on a decision".
- **Archived Specs are a place code must survive.** Two tests pinned paths
  under `docs/specs/<slug>/` and broke when a Spec archived: the legacy
  manifest characterization and the coverage record. Both now resolve the
  archive as a first-class home.

## Waiting on a decision

1. **Branch protection on `main`.** There is none, so no check can be
   required. The fix is one API call or one Settings page; `enforce_admins`
   should stay false so an emergency merge remains possible:

   ```bash
   gh api -X PUT repos/marcioaltoe/roundfix/branches/main/protection \
     -f 'required_status_checks[strict]=false' \
     -f 'required_status_checks[contexts][]=Verification gate' \
     -F 'enforce_admins=false' \
     -F 'required_pull_request_reviews=null' \
     -F 'restrictions=null'
   ```

2. **The verification performance contract** for adopting repositories,
   drafted but not yet filed: a per-profile Baseline clause contracting the
   two-tier gate and its budgets (local incremental ≤10s unchanged, ≤60s after
   a typical change; CI fresh and complete). It is intent, not observation, so
   it belongs in `docs/backlog/` as a `perf` entry once Spec 0075 creates that
   directory. The draft is not committed anywhere — it needs rewriting from
   this handoff and the archived 0071 report.

## Starting the next Spec

The queue's first entry is `0064-spec-artifact-consistency-gate`. It has a PRD
and a TechSpec; it needs `write-tasks`, and its graph should author its own QA
gate as a terminal `qa` node — Spec 0074's manifest is the worked example.

The mechanics, in order: branch, `write-tasks`, open and merge the graph's
Pull Request (the graph must be committed before `implement` can read it),
branch again for the work, `roundfix implement --spec <slug> --detach`,
integrate the Run Branch with `git merge --ff-only`, open the Pull Request,
wait for the reviewer's decision on the current head, then let the authored
gate run.
