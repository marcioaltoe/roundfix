# Protected-tooling Tasks demand a green repository and an undocumented commit choreography (2026-07-28)

A Task that edits protected tooling has to satisfy two conditions nothing in the
repository states, and failing either costs a Run plus a QA cycle. Both were hit
repeatedly on 2026-07-27 and 2026-07-28 across Specs 0037, 0038, and 0039 — by
Agents behaving correctly and by the supervisor, who got the choreography wrong
twice in a row while knowing the rule existed.

This is the general form of
[derived Skill digest pins have no regeneration path](2026-07-27-derived-skill-digest-pins-have-no-regeneration-path.md).
That finding covers one recurring content; this one covers the shape.

## Condition 1 — the whole repository must already be green

These Tasks declare `make verify` as their Verification. `make verify` is
repository-wide, so **any** unrelated red makes the Task unsatisfiable, and the
Task has no authorization to fix what is red.

Spec 0039 task_09: the Task's own work was correct and complete, but the gate
failed on `TestBranchIntegrityPreflightMigratesOutdatedRunDatabase`, which
pinned schema version `10` as a literal while that Spec raised the schema to
`11`. The test belonged to no Task in the graph. The Agent settled `failed` and
reported the blocker, which was the right call and the only one available to it.

The trap generalizes beyond digests and schema literals: a flaky test, a stale
fixture, or a lint rule tripped by another Task can strand a correct Task, and
the more scope-bounded the Task, the less it can do about it.

## Condition 2 — an undocumented commit choreography

Landing the change requires composing commits in an order and scope that no
guide describes, and the QA gate audits both:

1. Any supervisor fix needed to make the gate green must be its **own commit,
   before** the Task commit. Folding it in fails the Task's changed-path
   criterion.
2. The authorization record must be its **own commit, before** the Task commit
   it authorizes. Recording it afterwards fails the Tooling Authority audit —
   at the moment of the mutation, the artifacts still forbade it.
3. The authorization must not live inside the Task commit either, which would be
   circular: the commit authorizing itself.

The supervisor failed (1) on the first attempt and (2) on the second, on the
same Spec, and the gate caught both:

- `F-01`: the Task commit also contained `internal/cli/cli_test.go` and
  `internal/store/store_test.go`, absent from the authorization.
- `F-001`: the authorization commit landed 10 seconds **after** the Task commit
  that relied on it.

Only on the third attempt was the order right: prerequisite fix → authorization
→ Task → everything else.

## Why it matters

Each miss costs a full QA cycle — roughly twenty minutes of gate execution plus
the recovery — and none of the three misses was a defect in the product being
built. The cost is entirely process. It also scales the wrong way: the more
carefully a Spec bounds its tooling Task, the more likely the Task is
unsatisfiable and the more precise the choreography has to be.

Worth stating plainly: the Agents were right every time. They refused to exceed
their authorization, reported the blocker, and left the recovery to a human. The
defect is that Roundfix asks a bounded Task to satisfy an unbounded gate, then
asks a human to hand-assemble a commit sequence that only the QA gate knows the
rules for.

## Suggested resolution

1. Scope a tooling Task's Verification to what the Task can affect, or make
   "repository is green on entry" an explicit precondition the Implement Command
   checks and reports before assigning the Task — failing early with the real
   reason instead of after the Agent's work.
2. Document the commit choreography in `docs/agents/`, and have the
   Skill-alignment Task template state it, so it is a rule rather than folklore
   recoverable only from QA findings.
3. Better, remove the need for it: if the derived pins are regenerated by a
   sanctioned command and covered by a standing policy, conditions 1 and 2 both
   disappear for the common case.
4. Have the QA gate report all authorization-shape problems in one pass. The
   three attempts each surfaced one problem, so each fix revealed the next —
   scope, then order, then content.

## Suggested acceptance checks

- A tooling Task whose repository is red at assignment reports that precondition
  instead of failing on an unrelated test after the Agent works.
- A Skill-alignment Task lands in one attempt with no QA authorization finding.
- The commit choreography is discoverable from `docs/agents/` without reading a
  QA report.

## What worked — keep

- The QA gate audits the supervisor with the same rigor as the Agents, and it
  found a real ordering violation that a human reviewer would almost certainly
  have waved through. That non-deference is the property to protect.
