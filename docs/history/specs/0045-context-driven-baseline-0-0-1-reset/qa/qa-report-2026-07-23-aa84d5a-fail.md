## Findings

### F-01 — Clean Standard TypeScript Monorepo adoption bypasses the 0.0.1 contract

Impact: `Blocks-Completion`.

Actor and journey step: Repository Maintainer, clean setup preview and
confirmation for `standard-typescript-monorepo`.

Expected: local Repository Capability evidence must prove the exact required
stack and workspaces before mutation; missing PostgreSQL, LogTape, packages,
and workspaces must block. A successful apply must write only strict `0.0.1`
manifest/snapshot state and the exact frontend/backend architecture contract.

Actual: two independent repositories with no `package.json` or required stack
evidence previewed only `plan.confirmation.required`, then confirmed at exit
`0`. The emitted manifest used integer schema `1`, generator version `1`, and
baseline `baseline.portable-v3`; generated architecture guides retained the
older generic portable rules.

Public reproduction:

1. Create a disposable repository with `DESIGN.md`, a typed REST HTTP contract,
   and a complete strict `setup-context-driven/decisions/0.0.1` file, but no
   application package/workspace/capability evidence.
2. Run public `context_setup.py apply` with
   `--profile standard-typescript-monorepo --format json --decision-file`.
3. Confirm the returned digest with the same inputs.
4. Inspect `docs/agents/setup-context.json`, `docs/agents/frontend.md`, and
   `docs/agents/backend.md`.

Evidence: [E-06](evidence/2026-07-23-baseline-reset/evidence.md).

Affected rows: US-02, US-06, AC-05, AC-09, AC-11, AC-12, AC-13, SW-CLI,
SW-INFRA, and SW-DOCS.

Required repair: route clean profile adoption through the same strict 0.0.1
profile/capability/manifest integration proven by Readoption, then add a public
clean-repository regression that asserts required-capability blocking, exact
architecture carriers, strict manifest/snapshot identity, clean audit, and
empty reapply.
