## Findings

### F-001 — Nonblocking mechanical seed reports a refusal that did not happen

- Impact: `Trust-Damage`.
- Actor and journey: maintainer reading the real Daemon-seeded QA Report; R01
  before the Agent writes its matrix.
- Expected: a terminal refusal row records an actual blocking precondition. A
  nonblocking stage that starts the Agent does not claim `fail` or `mechanical
  refusal`.
- Actual: frontmatter initially said `verdict: pass`, the mechanical findings and
  assigned-repair failures were both `None`, and the Daemon started this Agent,
  but the materialized row says `QA-PRECONDITION | fail | mechanical refusal`.
- Reproduction: run this Spec's QA node with no carried or blocked mechanical
  rows and inspect the seeded report before Agent edits. The preserved row above
  is that production output.
- Root cause: `writeMechanicalQAReport` inserts the refusal row whenever
  `len(result.Carried)+len(result.Blocked) == 0`, without requiring
  `result.Blocking`. `mechanicalRefusalCause` then converts optional detector
  skips into a supposed refusal cause. The nonblocking writer test uses a carried
  row and does not cover the zero-row nonblocking case.
- Required change: materialize a refusal row only for an actual blocking result,
  or emit a truthful nonblocking seed row, then add a zero-row nonblocking
  writer-to-successor regression.
- Affected row: R01.
