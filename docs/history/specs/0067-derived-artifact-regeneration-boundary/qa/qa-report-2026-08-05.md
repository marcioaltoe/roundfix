## Findings

### F-001 — One sanctioned regeneration leaves Verification red

- Impact: `Blocks-Completion`
- Actor and step: Roundfix maintainer, Q-12, after changing an owned Skill and
  syncing its distributed mirror.
- Expected: one `make baseline-digests` invocation repairs every derived effect
  and leaves `make verify` green.
- Actual: the sanctioned command exited 0, but `make verify` exited 2 with
  seven failures because the dedicated plan-characterization goldens retained
  the old catalog digest. A second sanctioned run reported `changed: false`
  and did not repair the failures.
- Reproduction: in a fresh clone, edit `.agents/skills/qa-gate/SKILL.md`; run
  `rtk make skills-sync`; run `rtk make baseline-digests`; run
  `rtk make verify`; rerun `rtk make baseline-digests`.
- Evidence:
  [`owned-skill-regeneration.md`](evidence/2026-08-05-spec-0067/owned-skill-regeneration.md).
- Affected rows: Q-12.

### F-002 — Ownership records contradict the sanctioned command

- Impact: `Trust-Damage`
- Actor and step: maintainer reading the owner at the path, Q-10/Q-18, then
  running the ordinary owned-Skill regeneration journey.
- Expected: every record truthfully names one owner, and a `frozen` corpus is
  regenerated by nothing.
- Actual: the catalog-diagnostic record says it is not in
  `BASELINE_DIGEST_STEPS`, but `Makefile:110` includes its exact selector and
  flag. The parity record says nothing regenerates the corpus, but the
  sanctioned owned-Skill run rewrote `fixtures/asset-sync.json` and
  `manifest.json` below that record.
- Reproduction: read both records and `Makefile:104-110`; then repeat F-001
  through the first sanctioned run and inspect `git status --short`.
- Evidence:
  [`focused-boundary-checks.md`](evidence/2026-08-05-spec-0067/focused-boundary-checks.md)
  and
