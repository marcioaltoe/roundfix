# Task: Align every settle surface with the delivered contract

QA finding F-1 (`Trust-Damage`): settle now accepts a `completed` Task with
uncommitted work, but three of the five surfaces a Supervisor reads still
restrict it to failed Tasks, and one states the opposite of the delivered
behavior outright. The vocabulary the Spec changed — the Settle Command
glossary entry and the new `hook_refused` classification — is also absent from
the repository's domain context.

## Work

- `internal/cli/cli.go`: the one-line `settle` summary printed by
  `roundfix --help` states the two accepted states instead of "one failed Task".
- `CONTEXT.md`: the **Settle Command** glossary entry carries the delivered
  contract (failed, or completed with uncommitted work). Add `hook_refused` as
  an emitted classification beside the comparable entries already carried there
  (`agent_selection_failed`), so the term this Spec coined is documented where a
  reader looks it up. This is the closing node's glossary check, assigned by the
  PRD's Project Constraints and deferred by task_02's Result.
- `.agents/skills/roundfix/SKILL.md`: the settle paragraph stops telling the
  Supervisor that "completed Tasks have nothing to do" and states the accepted
  states. The path is inside the cited authorization's bounded paths; its
  mirror under `skills/` is regenerated by the declared `make skills-sync`,
  which the same authorization sanctions.
- Leave `roundfix settle --help` and `docs/user-guide/{commands,usage}.md`
  alone — task_02 and task_03 already carry the contract there.

### `CONTEXT.md` — the Settle Command entry and the `hook_refused` classification

The **Settle Command** entry (`CONTEXT.md:425`) carries the delivered contract:
it recovers a Task that is failed, or completed with uncommitted work, names the
three surfaces settle resolves in order, and states that a completed Task whose
surfaces are all clean was committed already and settles nothing. That matches
`settleSurfaceSettles` (`internal/cli/settle.go:399-414`), the refusal constant
`settle requires failed, or completed with uncommitted work`
(`internal/cli/settle.go:502`), and the `no uncommitted work` detail
(`internal/cli/settle.go:416`). The previous entry restricted settle to a failed
Task and to the current repository only; both were wrong against the delivered
command.

A new **Hook Refusal** entry (`CONTEXT.md:223`) sits directly beside **Selection
Failure**, the comparable classification entry the PRD's Project Constraints
point at, and follows the same shape — bold term, the token in backticks in the
first clause, `_Avoid_` line. Its claims are read from the delivered code, not
from the TechSpec's draft: the classification token
(`internal/daemon/commit_hook.go:12`), the Task staying `completed` with its
work staged and the Run reporting hook, exit code, output, and the recovery
command (`internal/daemon/task_engine.go:1633-1662`, asserted by
`TestTaskCycleHookRefusalKeepsTaskCompletedAndNamesRecovery`,
`internal/daemon/commit_hook_test.go:199`). The entry deliberately does not name
a Run outcome: the delivered boundary returns the refusal to the caller, and
naming `Unresolved` would state more than the code proves.
