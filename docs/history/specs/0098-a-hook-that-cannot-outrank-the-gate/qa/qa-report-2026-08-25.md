- **Impact**: `Trust-Damage`
- **Actor and journey step**: a Supervisor recovering after a hook refusal (US2)
  looks up what `settle` covers before running it.
- **Expected**: every surface that describes `settle` states the contract the
  Spec delivered — `failed`, **or** `completed` with uncommitted work.
- **Actual**: only `roundfix settle --help` and `docs/user-guide/{commands,usage}.md`
  were updated. Three surfaces still restrict `settle` to failed Tasks, and one
  of them states the opposite of the delivered behavior outright:
  - `internal/cli/cli.go:90` → `roundfix --help` prints
    `settle     Verify and commit all current worktree changes for one failed Task`.
  - `CONTEXT.md:422`, the **Settle Command** glossary entry and this
    repository's domain context: "The local recovery command that re-runs one
    **failed** Task's Verification commands in the current repository."
  - `.agents/skills/roundfix/SKILL.md:1961-1966` and its mirror
    `skills/roundfix/SKILL.md`: "no candidate surface has the target Task
    `failed` … `pending` and `in_progress` Tasks belong to the Implement
    Command; **completed Tasks have nothing to do.**"
- **Reproduction**: `roundfix --help | grep settle`; `sed -n '422p' CONTEXT.md`;
  `sed -n '1961,1966p' .agents/skills/roundfix/SKILL.md`.
- **Why this is in scope for this gate**: the PRD's Project Constraints assign

  introduced or changed one.**" The check ran and found one: the Settle Command's

  a new emitted classification, is also absent from the glossary while comparable
  classifications such as `agent_selection_failed` are carried there. The
  `spec check` vocabulary detector is in the **skipped** list, so it decided
  nothing. `task_02`'s Result already deferred the skill copy to "the Spec's
  closing Task"; this is that node, and QA may not make the edit.
  `.agents/skills/roundfix/SKILL.md` is inside the cited authorization's bounded
  paths, so a corrective Task can reach it.
- **Affected rows**: 14, 22 (and the discovery half of 3 and 17).

### F-2 — A hook that does not name itself is not classified, so the Run neither records `hook_refused` nor names the recovery — including in the repository where the three cases were measured

- **Impact**: `Trust-Damage`
- **Actor and journey step**: a Supervisor whose repository refuses a commit
  (US1). The Spec's Core Feature 1 promises the refusal "is detected and names
  the recovery"; the PRD's User Experience promises it "reports what the hook
  objected to **and what the loop did about it**".
- **Expected**: a `pre-commit` hook that refuses a verified commit is classified
  as a hook refusal, so the Daemon publishes the `hook_refused` Run Event and
  prints `roundfix settle --spec <slug> --task <task_id>`.
- **Actual**: `ClassifyCommitHookRefusal` (`internal/daemon/commit_hook.go:76`)
  decides only from the hook's own output, matching hook names or a runner
  banner (`husky`, `lefthook`, `.git/hooks/`, …). Git prints nothing identifying
  when a hook fails, so a hook that emits only its finding is **not** classified.
  `commitTask` (`internal/daemon/task_engine.go:1608`) reaches
  `recordHookRefusal` only through `errors.As(err, &refusal)`, so an
  unclassified refusal returns the raw error: no Run Event, no recovery line.
- **Reproduction** — observed live at the real settle commit boundary, as a
  clean A/B on the same code path:

  ```text
  # hook prints only its finding  → NOT classified
  roundfix: settle failed after verification: git commit -m feat: add the parser
  …failed: exit status 1: src/parser.go:3: function exceeds the 80-line limit

  # hook prints a runner banner   → classified
  roundfix: settle failed after verification: repository pre-commit hook refused
  the commit (exit status 1): internal/api/schema.gen.ts: 2462 lines exceeds the
  500-line limit
  husky - pre-commit script failed (code 1)
  ```

- **Why it matters more than a diagnostics gap**: the shape that fails to
  classify is the shape of the repository the Spec's Success Metrics were
  measured in. `/Users/marcio/dev/fluxus/.husky/pre-commit` is a plain
  `set -eu` script that shells out to `lint-staged` (husky `^9.1.7`, which
  prints no failure banner); the visible output is the linter's finding alone. A
  faithful reproduction of that shape — `core.hooksPath=.husky`, `set -eu` +
  lint-staged, oxlint-style output — was refused **unclassified**
  (`evidence/…/06`). The Run therefore ends without the `hook_refused` record and
  without naming `roundfix settle`, which is the "terminar `Failed` em silêncio"
  the source finding asked to eliminate. Combined with F-1, a Supervisor in that
  environment sees an unexplained git error, gets no recovery pointer, and finds
  three of five surfaces telling them `settle` does not cover completed Tasks.
- **What still holds**: the verified work is never lost. In every unclassified
  run the file stayed present and staged, `rev-list --count HEAD` was unchanged,
  and the task file stayed `completed`; `settle` then recovered it byte-identically.
  Goal 1 and Goal 2 survive; Core Feature 1's detection does not.
- **Scope note**: `task_01`'s Result discloses a narrower version of this — "a
  hook that refuses **silently** — no output at all". The measured gap is wider:
  a hook with plenty of output that simply does not name itself.
- **Affected rows**: 2 (fail); caveats recorded on rows 1 and 5.
