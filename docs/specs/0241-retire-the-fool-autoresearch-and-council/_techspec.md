# Retire the-fool, autoresearch and council — Technical Spec

## Executive Summary

A new set in `internal/baseline`, the Retired Skills (`council`,
`the-fool`), joins the repository-owned set the asset sync already holds. The
sync skips a Retired Skill both when it normalizes the upstream list and when
it re-appends recorded repository-owned entries, so a refresh from upstream
`b3c45a4`, which still lists both, writes snapshots without them (ADR-0246).
`context-workflow` drops both from `requiredSkills` and `skillDispatch`.
`council` then leaves the owned bundle, and this repository drops the vendored
`the-fool` and `autoresearch`. Finally `baseline update` reports retired
copies an adopter still holds, read-only. The primary trade-off is a
deliberate, named divergence between the snapshots and the upstream setup
lists in exchange for not editing upstream; the catalog tests keep the
divergence to the named set.

The design was prototyped on a disposable clone of `40a7893d` during
authoring: the module edit, the sync filter, the fixture transform and `make
baseline-digests` produced exactly the derived files listed in task_01, `go
test ./...` passed after the `council` removal, and the lock removal failed
only the two `skills/repository_test.go` tests task_02 changes.

  line 11 `skills/01-discovery/the-fool`; `rust.txt` the same lines;
  `typescript.txt` lines 91 and 100.

  entry. `buildAssetsSyncSnapshot` keeps a recorded `repo` entry even when

  longer shipped by the bundle`; the record command never drops a skill.

  14 Roundfix-owned, 29 external)`; after task_01 and task_02 the prototype
  printed `skills: ok (41 required: 13 Roundfix-owned, 28 external)`.
- Changing `skills-lock.json` changes the `declarationDigest` of two entries
  in `docs/agents/setup-context.json`, so the managed refresh runs again
  after the lock edit.
- `baseline skills reconcile` classifies a lock entry by whether its path
  exists upstream; `the-fool` still exists at `b3c45a4`, so reconcile would
  report it `present` and cannot remove it. The lock entries are deleted
  directly.

## Implementation Design

### Interfaces

```go
// internal/baseline/retired_skills.go
var retiredSkills = map[string]struct{}{"council": {}, "the-fool": {}}

// RetiredSkills returns the Retired Skills in lexical order.
func RetiredSkills() []string

// internal/baseline/retired_skills_installed.go
type InstalledRetiredSkill struct {
	Skill     string   `json:"skill"`
	Paths     []string `json:"paths"`
	LockEntry bool     `json:"lockEntry"`
}

// InstalledRetiredSkills lists, in lexical order of skill, each Retired Skill
// the repository still holds. It only reads.
func InstalledRetiredSkills(repoRoot string) ([]InstalledRetiredSkill, error)
```

```text
1. The asset sync skips an upstream entry whose normalized name is a Retired Skill before the duplicate checks, and skips a recorded repo entry whose name is a Retired Skill when it re-appends omitted repository-owned entries. No finding is added. Every other entry is handled exactly as before.
2. Paths holds, in this order, those of .agents/skills/<name> and .claude/skills/<name> that exist (os.Lstat, so a dangling link counts), as slash-separated paths relative to repoRoot. LockEntry is true when skills-lock.json has the key under "skills". A Retired Skill with no path and no lock entry is omitted.
3. A missing skills-lock.json means no lock entries. An unreadable or undecodable lock, or a Lstat error other than not-exist, returns an error that names the path.
4. baseline update calls InstalledRetiredSkills whenever it runs its skill checks: in the preview, after the drift comparison, and after an applied plan's skills stage. --no-skills skips it. An error is reported as the skill checks' existing execution failures are, with next action "repair skills-lock.json and rerun roundfix baseline update".
5. The result never changes state, category, message, next action or exit code.
6. Text output prints, after the Skills outdated block and only when the list is non-empty, "Skills retired: <n>" and one line per skill: "- retired <skill>: no longer required by the Baseline; delete <targets>". Targets are the Paths followed by "its skills-lock.json entry" when LockEntry is true, joined as "A", "A and B", or "A, B and C".
```

### The refresh procedure (task_01)

```bash
sha=b3c45a45f1bccd3b33aaecaaa22947d942f2fc02
src="$HOME/dev/skills"
git -C "$src" cat-file -e "$sha^{commit}" || { echo "stop: $src lacks $sha" >&2; exit 1; }
tmp="$(mktemp -d)"
git clone --quiet --no-local "$src" "$tmp/skills"
git -C "$tmp/skills" checkout --quiet --detach "$sha"
git -C "$tmp/skills" remote set-url origin https://github.com/marcioaltoe/skills.git
go run -buildvcs=false ./cmd/roundfix baseline assets sync --source-dir "$tmp/skills/setups" --format text
go run -buildvcs=false ./cmd/roundfix baseline assets sync --check --source-dir "$tmp/skills/setups" --format text
```

removes the two names from the three setups of
`internal/baseline/testdata/parity-corpus/v1/fixtures/asset-sync.json`, and

go run -buildvcs=false ./cmd/roundfix baseline update --repo . --no-skills --yes --format text

## Risks & Considerations

- 0239 may edit `context-workflow.json`, `write-prd` and `CONTEXT.md`; this
  Spec touches only the lines that name the retired skills, and the owned
  version record is regenerated at merge (ADR-0233).

  no-op for that name; a later change can drop it from the set.
- The removal instruction deletes the lock entry by hand because of the
  skills CLI behavior in the outside evidence; if the CLI fixes it, the
  instruction still works.
