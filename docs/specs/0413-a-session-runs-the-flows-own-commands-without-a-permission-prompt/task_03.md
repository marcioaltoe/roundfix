# Task 03: `roundfix permissions` shows the list for a harness and writes it only with the digest a preview printed

## Overview

This Task adds the command a person runs: `roundfix permissions` prints the plan of task_02 for one harness, or for every harness the repository holds, as text or JSON, and writes or removes the list only when it is given the digest that preview printed. The Roundfix skill gains the rule for when a session may apply the list, the user guide gains the command's page, and the glossary gains the four terms the surfaces name. It is demoable on its own: in a temporary repository the preview, the apply, the stale digest and the removal each print what the API Contracts fix.

## Requirements

1. MUST add `internal/cli/permissions.go` with `roundfix permissions` as `_techspec.md` → API Contract 1 states: the flags `--harness <claude|codex|opencode>`, `--remove`, `--apply <digest>` and `--format <text|json>`; with no `--apply` it previews the named harness, or every harness `Present` returns, or, when none is present and none is named, prints `No harness files in this repository. Name one with --harness.` and exits `0`; `--apply` requires `--harness` and refuses `opencode`; the exit codes `0`, `1`, `2` and `3` and the help text exactly as API Contract 1 gives them. The command needs a Git repository root, loads no Project Config and no User Config, and exits `2` outside a Git repository. Refusals go to standard error.
2. MUST print a preview with the fixed lines of `_techspec.md` → API Contract 2, in its order, for Claude Code, Codex and OpenCode, and for a removal, with the counts and entries of the plan. MUST add to `CONTEXT.md`, through the `domain-modeling` skill, right after the entry of **Undeclared Governed Path** and in this order, the entries of **Flow Command List**, **Named Exclusion**, **Guard Entry** and **Harness Permission File**, each a `**Term**:` line, one definition line, an `_Avoid_:` line and a blank line, with these definitions:
    - **Flow Command List**: "The closed list of commands that a session driving the flow may run without a permission prompt once a project applied it: each top-level `roundfix` subcommand an owned skill names and each Git or GitHub read an owned skill names, less every Named Exclusion. An entry names a command down to its subcommand and never constrains its arguments. The list ships inside the binary, and `roundfix permissions` shows it in the rule syntax of an Agent harness and writes it into a Harness Permission File only with the digest of a preview the user saw. It removes prompts and is not a security boundary." `_Avoid_: allowlist, standing authorization, permission preset`
    - **Named Exclusion**: "A command an owned skill names that the Flow Command List leaves out on purpose, shown with its reason in every preview: the command that applies the list, a `roundfix` subcommand the Roundfix skill runs only after asking the user, and every Git or GitHub command that changes the repository, its configuration, GitHub or the user's credentials. A harness keeps asking before it runs one." `_Avoid_: denied command, blocked command`
    - **Guard Entry**: "A rule beside the Flow Command List that keeps one option of a listed read asked about, such as writing the output of `git show` to a file or sending a body with `gh api`. Claude Code reads it from its ask list, where it wins over the entry it guards in every permission mode; Codex rules match only the start of a command, so its rendering holds no Guard Entry and its preview says so." `_Avoid_: deny rule, option filter`
    - **Harness Permission File**: "A file of the repository from which an Agent harness learns which commands a session may run without asking: `.claude/settings.json` or `.claude/settings.local.json` for Claude Code, a file under `.codex/rules/` or `.codex/config.toml` for Codex, and `opencode.json` or `opencode.jsonc` for OpenCode. `roundfix permissions` writes only `.claude/settings.json` and `.codex/rules/roundfix-flow.rules`, and opens no file under the user's home directory." `_Avoid_: settings file, rules file, harness config`
    The TechSpec's Build Order puts the fourth term with the governed set; it is defined here because the page of requirement 9 already names it. No other entry changes.
