# An audit that reads the authorization it was given

The changed-path audit refuses any file a Task commit touched that the
authorization record does not name. It refuses two kinds it should not. Derived
artifacts regenerated by the sanctioned command are refused, although an accepted
decision already settles that they are deterministic fallout of the authorized
edit and need no separate authorization — so the workaround is to list every
consequence in the record, which is exactly what that decision rejected when it
kept the grant drawn around the cause. And production code is refused, because the
audit reads every changed path as governed, which forced one Spec to split a Task
whose only fault was touching an ordinary Go file alongside an authorized asset. A
third disagreement sits beside them: the PRD template tells an author to record
`applicable` when no tooling changes, and the detector refuses that exact wording.

## Project Constraints

- Identifier strategy: applicable — Tooling Authority and Project Constraint are
  glossary terms whose reading this Spec sharpens, and the distinction between a
  governed path and an ordinary one may need vocabulary the glossary does not
  carry. The closing node checks whether the work introduced or changed a term.
  Source: `docs/agents/domain.md`.
- Authentication and HTTP: not applicable — no network boundary, credential or
  request is created or read. The work is static analysis of commits, records and
  authored artifacts. Source: `docs/agents/specific-repository.md`.
- Active ADR obligations: applicable — ADR-0081 is the decision the audit fails
  to implement: derived pins regenerated by the sanctioned command are fallout of
  the authorized edit, hand-edited pins remain unauthorized, and the grant stays
  drawn around the cause with its computable effects following it. ADR-0096 places
  this audit in the gate's mechanical stage, and ADR-0117 puts a check with the
  stage that can produce its defect, which is what moving the tooling-row
  contradiction to authoring time honours. This Spec's own decisions are ADR-0129,
  which lets a grant name the command while the tree names its outputs, ADR-0130,
  which makes the audit judge governed paths and holds the declared set to every
  path an authorization has ever bounded, and ADR-0131, which settles the tooling
  row as a statement of applicability rather than of mutation. ADR-0128 already
  made the audit and the suite guard read one regeneration declaration, and this
  Spec depends on it unchanged. The closing node rests on two more it follows
  rather than changes: ADR-0091 makes the QA gate a Task node of its own type, and
  ADR-0104 makes a Spec accept on evidence it did not author, which is what the
  two replayed historical refusals supply here. Source: `docs/agents/domain.md`.
- Tooling authority: not applicable — the audit and detector corrections are
  production Go, which no tooling grant governs. If the TechSpec resolves the
  template-versus-detector disagreement by changing the `write-prd` template
  rather than the detector, that becomes a protected tooling mutation and must
  obtain express maintainer authorization with exact bounded files before
  decomposition. Writing this row as `applicable` without a grant is itself
  refused by `SC-TOOLING-UNBOUNDED` — this Spec was refused that way while being
  authored, which is the third defect it records. Source:
  `docs/agents/agent-instructions.md`.

## Goals

1. A derived artifact regenerated by the sanctioned command passes the audit
   without being enumerated.
2. Production code is not audited as though it were governed tooling.
3. An author following the PRD template passes the checker.

## User Stories

1. As a Supervisor whose authorized Task regenerated derived pins, I want the
   audit to accept them, so that the authorization record names the cause rather
   than every consequence.
2. As a Supervisor whose Task touched an ordinary Go file and an authorized asset,
   I want the audit to judge only the asset, so that I do not split a Task to
   satisfy a check rather than a contract.
3. As an author writing a PRD for a Spec that changes no tooling, I want the
   template's own wording to pass, so that the first artifact I write does not
   refuse.
4. As a maintainer reading an authorization record, I want it to state what it
   permits rather than list what will happen, so that it stays auditable as it
   grows.

## Core Features

1. **Sanctioned fallout passes.** A derived artifact the sanctioned regeneration
   command rewrites is recognised as fallout of the authorized source edit, and a
   hand-edited derived value is still refused — the distinction the accepted
   decision already draws and the audit cannot currently make.
2. **Governed and ungoverned paths are told apart.** The audit judges paths the
   tooling rules govern, and does not refuse a changed path that needs no
   authorization at all.
3. **The template and the detector agree.** One of the two changes so that a
   Spec with no tooling mutation has a wording that both the template teaches and
   the checker accepts.
4. **The tooling row means one thing.** Whether `applicable` means "this
   constraint governs this Spec" or "this Spec mutates tooling" is settled, since
   the detector reads the second while the template writes the first.

## Non-Goals / Out of Scope

- Weakening the tooling-authority rule, or widening what a grant permits. This
  Spec makes the audit read the grant correctly; it does not make grants broader.
- Changing where the audit runs, or the gate's mechanical stage beyond this check.
- Changing the authorization record's frontmatter contract, which a checker
  already enumerates successfully.

## Success Metrics

- A Task that regenerates derived artifacts through the sanctioned command passes
  the audit with those artifacts absent from the record, reproduced from the
  measured refusal of 2026-08-13.
- A Task touching one authorized asset and one ordinary Go file passes without
  being split.
- A PRD written verbatim from the template's no-tooling wording passes
  `spec check --stage prd`.
- A hand-edited derived pin is still refused.

## Decisions

- The audit is corrected rather than the records widened. Listing consequences in
  a grant is the workaround this Spec exists to remove.

## Open Questions

- How the audit tells a governed path from an ordinary one. A declared set of
  governed prefixes is the simplest and the most likely to drift; deriving it from
  the same source the tooling rules name is harder and stays true.
- Which side of the template disagreement changes. Changing the template is
  smaller and matches what already passes; changing the detector preserves the
  template's reading that the constraint is applicable to every Spec.
