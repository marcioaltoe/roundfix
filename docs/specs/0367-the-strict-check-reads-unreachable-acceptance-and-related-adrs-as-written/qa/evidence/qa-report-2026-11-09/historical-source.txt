# A rerun finishes a partial npm publication

Twice the release workflow's npm publication stopped part way: v0.130.0 published one platform package and v0.132.1 published all five before `npm publish` failed with `(409) an equivalent entry already exists in the transparency log`. Each time, the rerun of the failed job refused in the Publication Preflight with `registry: <package>@<version> is already used` for every package the first attempt had published, so the version was abandoned and the next patch republished the same changes. After this Spec the preflight reads a package already published at the target version as `published`, the tag run compares its published content with its own build, and the rerun publishes only the packages that are missing; a package published with different content still stops the release before anything publishes.

## Goals

- The rerun of a release job whose npm publication stopped part way
  publishes only the packages that are missing and completes the release.
- A package already published at the target version is accepted only when
  its published content is byte-identical to this run's build; any other
  answer stops the release before anything publishes.
- A version that was published and then unpublished, a cooldown, an absent
  package and an unreadable registry answer keep stopping the preflight as
  today, and a release whose six packages are all published stops with its
  own reason.
- The release runbook tells the maintainer how to finish a partial
  publication and what a refusal means.

## User Stories

1. As the maintainer, I want to rerun a failed release job after a
   transparency-log 409 and see the release complete, so that I do not have
   to cut and announce the next patch for the same changes.
2. As the maintainer, I want a rerun to refuse when a published package does
   not hold the same content as the rebuild, so that a release never mixes
   two builds.
3. As the maintainer reading the runbook, I want the recovery steps and the
   meaning of each `registry:` refusal, so that I know when a rerun can
   succeed and when only the next version can.

## Core Features

1. The Publication Preflight classifies a version listed under `versions` as
   `published`, which does not stop it, and keeps `used` for a version listed
   only under `time`; it stops when all six coordinates are `published`.
2. A new tag-run step, after the build and before any publish, compares each
   `published` coordinate's decompressed tarball with this run's packed
   build and stops on a difference or an unreadable tarball.
3. The publish step skips each coordinate that compared equal.
4. Documentation: the release runbook gains the recovery procedure and the
   new refusals; `CONTEXT.md` updates **Release Set** and **Publication
   Preflight**; ADR-0146 carries the amendment notice.

## User Experience

On the rerun of a v0.132.1-shaped failure the job log shows the preflight
table with five `published` rows and `roundfix ... eligible`, the step
"Compare published packages" prints five `same content` rows, and the
publish step prints `skipping <coordinate>@<version>: already published with
the same content` five times and then publishes `roundfix`. The job summary
gains an "Already published" section. A different build stops in "Compare
published packages" with `registry: <coordinate>@<version> is already
published with different content (registry <integrity>, this build
<integrity>)`.

## Non-Goals / Out of Scope

- Retrying `npm publish` inside the job after a `TLOG_CREATE_ENTRY_ERROR`;
  ADR-0374 records it as a considered option, and it needs its own
  decision.
- The Go and Node versions the workflow installs (`check-latest: true` on
  setup-go stays); a rerun after a new Go patch release is refused as
  different content.
- The GitHub Release step, the token fallback and its window, the
  `workflow_dispatch` rehearsal's place before the build, and any change to
  `make verify`, `make verify-contracts`, the Makefile, `go.mod`, `go.sum`
  or lint and formatter configuration.
- Publishing anything to npm or creating a tag or a GitHub Release from this
  Spec's Tasks or QA.

## Success Metrics

1. Success Metric: with the v0.132.1 shape (five platform packages
   published with the same content, the launcher eligible) the preflight,
   compare and publish steps exit 0 and `npm publish` runs once, for
   `roundfix`; at `cb3ed035` the preflight exits 1 with five
   `registry: <coordinate>@0.132.1 is already used` lines.
2. Success Metric: with the v0.130.0 shape (one platform package published
   with the same content) the publish step publishes the four other platform
   packages and then `roundfix`, in that order.
3. Success Metric: a published tarball whose decompressed content differs
   stops "Compare published packages" with the `different content` line and
   no `npm publish` runs; a published tarball that differs only in its gzip
   bytes compares equal.
4. Success Metric: a version listed only under `time` still stops the
   preflight with `registry: <coordinate>@<version> is already used`; six
   published coordinates stop it with `registry: every coordinate of the
   Release Set is already published at <version>`; a cooldown keeps its
   line.
5. Success Metric: a `TLOG_CREATE_ENTRY_ERROR` from `npm publish` stops the
   publish step under `publish:` after one attempt and never starts the
   token fallback, as at `cb3ed035`.

## Acceptance evidence

The outside-evidence row rests on a source this Spec did not write: the npm
CLI documentation for `npm publish`
(https://docs.npmjs.com/cli/v11/commands/npm-publish/, read through Exa on
2026-11-06): "Once a package is published with a given name and version,
that specific name and version combination can never be used again, even if
it is removed with `npm unpublish`." A rerun can therefore never republish a
coordinate the first attempt published; it can only skip it, and a version
removed by `npm unpublish` can never be completed.

## Unreachable Acceptance

1. A real rerun of a failed release job on GitHub Actions against the npm
   registry: it would publish packages, which this Spec's authorization and
   its QA forbid. The QA proves the same path on the workflow's own step
   scripts with a stub registry and records this as one blocked row.

Taken from those and the evidence, with no further interview:

- "A mesma integridade" is proven by the decompressed tar stream, not by
  the npm `dist.integrity`, because the measured integrity differs between
  machines for identical content (ADR-0374).
- The comparison runs after the build on a tag run; the preflight stays
  before the build (ADR-0146) and only classifies.
- The workflow never retried the failed publish, so no retry is removed;
  an in-job retry stays out of scope.
- ADR-0374 amends ADR-0146, and a non-QA Task writes the notice into it.
- The release is the operator's patch right after the merge; no Task
  releases or publishes.
