# A decision that reaches every artifact

The Baseline's preservation path and its greenfield path disagree about what a
decision means. Answering a decision so that it excludes an artifact drops that
artifact from the manifest and leaves its bytes on disk with the setup markers
intact, so the repository states a rule the Baseline no longer recognises, in a
file whose markers claim setup owns it. Greenfield is unreachable for any
repository with stale managed carriers, which is precisely the population most
likely to re-adopt. Changing the HTTP Contract discards every recorded exception
silently, on the only path a maintainer can change the mode. A second declaration
of the same default sits inert with an unimplemented error code that makes it look
load-bearing. Preflight warns on the Baseline's own fixtures every run, teaching
its reader to skip the one warning class that also carries the real signal. And
the manifest's recorded catalog digest — its only claim about provenance — is
compared against nothing, so a catalog edit leaves it naming a catalog that is
gone while the gate passes.

## Project Constraints

- Identifier strategy: applicable — Setup Manifest, Managed Region, Managed
  Carrier, Source Baseline, and HTTP Contract Decision are glossary terms this
  Spec changes the lifecycle of, and a deletion planned from an excluded artifact
  may need vocabulary the glossary does not carry. The closing node checks whether
  the work introduced or changed a term. Source: `docs/agents/domain.md`.
- Authentication and HTTP: applicable — the HTTP Contract Decision is the
  repository's declared HTTP policy vocabulary, and this Spec changes how its
  exceptions and provenance survive a change. It sets no policy itself and adds no
  transport, client, or credential; the values remain the adopting repository's.
  Source: `docs/agents/specific-repository.md`.
- Active ADR obligations: applicable — ADR-0081 makes derived pins regenerated by
  the sanctioned command deterministic fallout of the authorized edit, which is
  what lets a manifest refresh follow a catalog change rather than becoming its own
  governance amendment; ADR-0099 makes retention accounting mechanical while
  instruction classification is not, which is the split an exclusion-planned
  deletion must respect — it may compute what left the manifest and must not
  decide what a maintainer meant. ADR-0129 lets a grant name its regeneration command while the tree names that command's outputs; this Spec authors Baseline decisions and digests rather than reading a grant, so it does not apply. Source: `docs/agents/domain.md`.
- Tooling authority: applicable — the decision catalog, a profile asset, the
  source-baseline manifest, and this repository's Setup Manifest are edited.

## Goals

1. A decision that excludes an artifact removes it, so no repository states a rule
   the Baseline no longer recognises.
2. Every adoption mode is reachable for the repositories most likely to use it.
3. Changing a decision preserves everything the maintainer already recorded under
   it.
4. A warning that always fires stops existing, so the class stays readable.
5. The manifest's provenance claim is checked rather than believed.

## User Stories

1. As a maintainer flipping a decision to exclude an artifact, I want its bytes
   and its root pointer removed, so that an Agent does not read retired guidance
   whose markers claim setup owns it.
2. As a maintainer of a repository adopted under an older catalog, I want
   greenfield adoption to complete, so that the mode is a slower route rather than
   an unreachable one.
3. As a maintainer changing the HTTP Contract mode, I want my recorded exceptions
   and their provenance to survive, so that changing one field does not cost me
   every other.
4. As a maintainer running the Baseline in this repository, I want no warning
   about its own fixtures, so that the warning class still means something when it
   fires.
5. As a maintainer reading the manifest, I want its recorded catalog digest to be
   true, so that a stale one cannot claim the guides are current for a catalog that
   is gone.

## Core Features

1. **Exclusion plans its deletion.** A decision that excludes an artifact plans
   the removal of that artifact and strips its orphaned managed region from any
   shared carrier, so preservation converges with greenfield rather than diverging
   from it.
2. **Greenfield accounts for stale managed carriers.** Greenfield adoption either
   handles them without classification, or refuses up front naming the mode that
   can, rather than failing at a gate it structurally cannot pass.
3. **A decision change carries its recorded values.** Changing the HTTP Contract
   mode preserves the recorded exceptions and provenance, or edits them
   explicitly; it never drops them silently.
4. **The inert default is settled.** The duplicated default in the profile asset
   is read, deleted, or made a real override, and its unimplemented error code is
   resolved with it.
5. **Carrier discovery excludes the Baseline's own fixtures.** A fixture that
   holds marked bytes because it is a fixture of marked output is not reported as
   a nested carrier conflict.
6. **The provenance claim is checked.** The manifest's recorded catalog digest is
   compared against the catalog the repository ships, and a drift is reported by
   the gate rather than passing.

## User Experience

A plan that excludes an artifact lists the deletion and the region it strips, and
asks before removing repository bytes. A decision change presents the recorded
values it will carry forward. A drifted manifest digest is named with the command
that refreshes it.

## Non-Goals / Out of Scope

- Changing the decision set, the profiles, or any decision's default value.
- Changing what a Managed Region is or how retention evidence is computed.
- The relocation of the archive root, which is its own Spec.
- Moving the canonical method out of the rendered guides, which is a separate
  Spec.
- Any repository's own HTTP policy content.

## Success Metrics

- Flipping a decision to exclude an artifact removes it, reproduced from the
  measured case on 2026-08-10 where the artifact and its root pointer both
  survived.
- A repository with stale managed carriers completes greenfield adoption, or is
  refused up front naming preservation, measured against the repository reported
  on 2026-08-07 that reached alignment with zero divergences and then failed.
  Source: a repository this Spec did not build.
- Changing the HTTP Contract mode preserves the four exceptions and the source
  recorded in the measured repository.
- A plan and an apply in this repository emit no fixture-owned carrier warning.
- A manifest whose recorded digest does not match the shipped catalog fails the
  gate.

## Decisions

- The provenance check is added here rather than in the archive Spec that first
  meets the drift, because the drift originates in the catalog-to-manifest
  derivation this Spec owns.

## Open Questions

- Whether an excluded artifact is deleted outright or reported as an orphan for
  the maintainer to confirm. Confirming is the default until answered, because
  deleting repository bytes on a decision flip is the kind of change the Baseline
  otherwise asks about.
- Whether the fixture exclusion is path-based or declared by the assets' own
  ownership records. The ownership records are the default until answered, since
  they already state which trees are fixtures.
- Whether the digest drift fails the gate or reports as a warning. Failing is the
  default, since a provenance field nobody checks is the field most likely to be
  believed without evidence.
