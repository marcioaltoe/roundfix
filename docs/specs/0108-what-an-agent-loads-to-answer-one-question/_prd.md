# What an Agent loads to answer one question

The canonical method is delivered by rendering prose into per-repository guides
that each repository then personalises in the same files: measured here, 103 KB of
catalog JSON renders 1,450 lines into thirteen files that also hold 41 local
rules, and most of an update plan's output is the retention evidence proving it
did not eat them. The skill channel already carries canonical content with none of
that machinery, and its contract tests caught five real regressions in one day.
Separately, the operational skill is 2,172 lines across 29 sections — six times
the next largest — so an Agent resolving a review comment loads release planning,
retention policy and the whole configuration reference alongside what it needs.
The move is obvious and the shape is not: a guide is always-on and a skill is on
demand, and mandatory dispatch is itself unverified prose.

## Project Constraints

  are where the glossary's terms are used most, and a clause that moves must keep
  naming concepts the glossary owns. The closing node checks whether the work
  introduced or changed a term. Source: `docs/agents/domain.md`.
- Authentication and HTTP: not applicable — no network boundary, credential, or
  request is created or read. The work redistributes instruction content and
  changes what is loaded when. Source: `docs/agents/specific-repository.md`.
- Active ADR obligations: applicable — ADR-0093 checks Spec consistency by
  citation rather than inference, which is the standard a relocated clause's
  enforcement must still meet; ADR-0117 places a check with the stage that can
  produce its defect, which is the division this Spec applies to instruction

## Goals

1. An Agent answering one question loads what that question needs.
2. Canonical content reads the same in every adopting repository, and local
   personalisation has its own home.
3. A clause that governs every task and has no check stays always-on and minimal.
4. Dispatch becomes checkable, or nothing moves that depends on it.

## User Stories

1. As an Agent resolving a review comment, I want to load the review contract
   without the release, retention, and configuration references, so that context
   is spent on the work.
2. As a maintainer adding a rule to the operational skill, I want a file where the
   rule has an obvious home, so that placement is not a search through two
   thousand lines for an anchor.
3. As a maintainer updating the Baseline, I want the update to be a version bump
   rather than a diff-and-merge over managed regions, so that retention evidence
   stops being most of the output.
4. As an Agent governed by a clause that used to be always-on, I want dispatch to
   be verified, so that moving the clause into a skill does not quietly weaken it.

## Core Features

1. **Content divides by enforcement, not by canonicity.** A clause a mechanical
   check already decides may live wherever it is cheapest to read; a clause that
   governs every task and has no check stays always-on and minimal; a clause
   governing one kind of work belongs to that skill; repository personalisation
   has its own file.
2. **Dispatch is checkable before anything depends on it.** A clause moves into a
   skill only once dispatch to that skill is verified rather than asserted; until
   then, it stays where it is.
3. **The operational skill routes rather than carries.** Its independent subjects
   move into references beside it, with the skill keeping what routes.
4. **The cost is measured before it is assumed.** How much of the operational
   skill a typical dispatch actually uses is measured, and that number decides
   whether the split is a real saving or a tidiness preference.

## User Experience

An Agent dispatched for one subject loads the routing skill and the one reference
it names. A maintainer adding a rule has one file per subject to choose from.

## Non-Goals / Out of Scope

- Changing any clause's content. This Spec moves clauses and changes where they
  live; a rule that should say something different belongs to the Spec that owns
  it.
- Removing the Baseline's rendering of guides, which stays for whatever the
  division leaves always-on.
- Changing the skills' own behavior, their triggers, or their versioning contract.
- Any change to how skills are synchronised or their digests derived.

## Success Metrics

- The measured share of the operational skill a typical dispatch uses is recorded,
  and the split is decided against it rather than against its line count.
- No clause moves into a skill while dispatch to that skill is unverified.
- A dispatched Agent loads fewer subjects than today for the same task, measured.
- Every clause that moves keeps the same enforcement it had, proven by exercising
  its check before and after.
- The five regressions the skill contract tests caught on 2026-08-09 would still
  be caught after the split. Source: a measured day outside this Spec's artifacts.

## Decisions

- Dispatch verifiability gates the move, because a clause in an always-on guide
  governs every task while a clause in a skill governs only a dispatched one, and
  trading a weak guarantee for a weaker one is the failure this Spec must not
  cause.

## Open Questions

- Whether each part of the method gets its own skill or one skill carries the
  method with a references directory. One skill with references is the default
  until answered, because it keeps one dispatch to verify.
- Whether this Spec extends or supersedes part of the Spec that already owns what
  an Agent reads. The default is to extend, and to state the supersession
  explicitly if the division contradicts it.
- What makes dispatch checkable. This is settled before any clause moves, and if
  it cannot be, the Spec delivers the operational skill's split alone.
