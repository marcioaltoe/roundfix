# A review finding anchored as path:line and a period blocks the item

## Symptom

On 2026-11-11 the pre-PR review of Spec 0376 (Roundfix 0.139.1, provider `codex`) answered two findings, each starting with an anchor followed by a period, for example `docs/user-guide/commands/skills.md:34. Failure: …`. Roundfix read neither anchor, so the review ended `blocked` with the reason `findings name no file and line` and the Delivery Queue parked the item as `review-blocked`. Both findings were real and anchored in the candidate diff.

## Where

`parseReviewFindingAnchor` in `internal/cli/review_validation.go`: after the `path:line[-line]` match it accepts only a space, `:`, `,` or `)` as the next character, so a sentence-ending `.` (and likewise `;`) makes the anchor unreadable.

## Expected

An anchor followed by a period or a semicolon is read like one followed by a space, so such findings are validated against the candidate diff instead of blocking the item. A path that itself ends in a period-like suffix must still parse as the whole path.

## Evidence

Review record `~/.roundfix/artifacts/339f8dac2b687a04/pre-pr-review/69ca9a33cab51858/` on the mini: `pre-pr-review-answer.txt` holds the two findings; `pre-pr-review.json` has `outcome` `blocked` and `reason` `findings name no file and line`. The operator fixed both findings on the item branch and retried.

# The delivery owner crashes when the repository gate waits for Machine Verification

## Symptom

On 2026-11-12 at 10:20 UTC, Roundfix 0.141.1 on the Mac mini reached the repository gate for Spec 0382 while a Quaestor Run held the only Machine Verification Capacity slot. The detached Delivery Owner then failed with `panic: runtime error: invalid memory address or nil pointer dereference` in `fmt.Fprintf` and exited. `roundfix deliver status` kept reporting the item as `gating` with no owner for about 8.5 hours, and no status line showed that the owner was gone. `roundfix deliver resume` started a new owner, and the item continued.

## Where

`commandDeliveryEngineDependencies` in `internal/cli/deliver_workflow.go` builds `commandDeliveryWorkflow` without setting `log`; only tests and `deliver lane` set it. `Gate` writes to `workflow.log` with no nil check in three places:

- the Machine Verification wait callback, which panicked here;
- the shared-cache trim report;
- the lease-release warning.

The item-binary probe already falls back to `os.Stderr` when `log` is nil.

## Expected

- The production workflow always has a log writer, the owner's console log, so every item whose gate waits for capacity logs the wait instead of crashing.
- `deliver status` reports a queue whose recorded owner is no longer running instead of showing the item as still active.

## Evidence

- On the mini, the owner's console log is at `~/.roundfix/artifacts/339f8dac2b687a04/delivery/delivery-339f8dac2b68-49802/console.log`. Its stack trace names `deliver_workflow.go:1713` (`Gate.func1`) called from `store.AcquireMachineVerification`.
- The defect has existed since Spec 0374 added the capacity wait at the gate. Until now it went unseen because the gate rarely waited.

# An ADR marked as not applying in Portuguese still seeds the related ADRs

## Opportunity

An adopter that writes its Specs in Portuguese could mark an ADR as not applying in its own words and have the strict check read it. ADR-0377 reads one fixed leading token, `not applicable`, in the TechSpec's `## ADR Alternatives` line, through `notApplicableRelationPattern` in `internal/speccheck/authoring_proof.go`.

## Value

Fiscus reported on 2026-11-10 that the 76 ADR lines behind the cascade Spec 0367 fixed use "não se aplica". The strict check of its Spec 0081 reports no finding on Roundfix 0.137.6, so nothing fails today. Those lines are still read as applied ADRs, so the amendment of ADR-0377 does not shorten the related-ADR closure for a Portuguese Spec until its author rewrites each line with the English token. The hypothesis is that reading the adopter's own marker saves that rewrite and keeps the closure small for every Portuguese Spec.

## Shape

Non-binding. A small closed list of leading tokens that includes the Portuguese form; or a Project Config key that names the adopter's token; or no code change and a line in the `write-techspec` skill that prescribes the English token whatever the Spec's language. ADR-0377 rejected a marker phrase in the PRD row because "a phrase written in one Spec's language binds no other", so a Spec that takes this up amends that ADR.

# A user-level skill copy older than the project copy is loaded unnoticed

## Symptom

On 2026-11-10 a Claude Code session in this repository ran `/roundfix --follow-up` and received the Roundfix skill at version 0.1.140 from the user-level skills directory. The repository copy in `.agents/skills/roundfix`, which `.claude/skills` links to, was at 0.1.208, the version Roundfix 0.137.7 ships. The loaded text had no `--update` Skill Mode, no handoff claim in the follow-up mode and no Waiting Items. Seven more owned skills were behind in the same way: `qa-gate` 0.0.19 against 0.0.25, `write-tasks` 0.0.19 against 0.0.31, `write-prd` 0.0.13 against 0.0.18, `write-techspec` 0.0.14 against 0.0.18, `archive-spec` 0.0.14 against 0.0.19, `implement-task` 0.0.5 against 0.0.6 and `setup-context-driven` 0.0.6 against 0.0.8. The user-level copies dated from 2026-10-26, and `roundfix skills check` passed.

## Where

`roundfix skills install --target <claude|codex|opencode|all>` writes the user-level copies. `roundfix upgrade`, `roundfix update check`, the `--update` Skill Mode and `roundfix baseline update` refresh the binary and the project's `.agents/skills` and never those copies. `roundfix skills check` compares the project copies. Claude Code loads a user-level skill in place of the project skill of the same name, so one stale copy wins in every repository on the machine.

## Expected

A user-level copy of a Roundfix-owned skill that is older than the copy the installed binary embeds is reported with the command that refreshes it, by `roundfix skills check`, by `roundfix doctor` and by the Update Check, or the path that upgrades Roundfix refreshes the copies it installed. Whether to report or to refresh, and which harness directories to read, are choices for the Spec.

## Evidence

The maintainer approved a refresh; after `roundfix skills install --target claude` the twelve owned skills matched the repository copies.

# The disk-full tests read a real host path

## Symptom

`TestTheItemBuildOnAFullDiskIsADiskFullFailure/path_in_the_log` and `TestTheRepositoryGateOnAFullDiskParksDiskFull/full_disk` fail on a machine where `/tmp/x` exists as a regular file. Spec 0365 lost its first Run this way on 2026-11-09 (Run `run_20261109T120541Z_75e62679b1abfda6`, task_01, `make verify-changed`): an empty `/tmp/x` file created on the maintainer's MacBook earlier that morning made the reported free space `0 MiB` instead of the stubbed value, and the item parked `run-unresolved` for a defect the Spec did not touch.

## Where

`internal/cli/deliver_disk_full_test.go` writes the literal path `/tmp/x/_pkg_.a` into the fake build output. `internal/cli/deliver_disk_full.go` `diskFullFailure` calls `doctorDiskSpaceAncestor` on that path before the stubbed `availableBytes`; `os.Stat` on `/tmp/x/_pkg_.a` returns `ENOTDIR` when `/tmp/x` is a file, which is not `os.ErrNotExist`, so the ancestor lookup fails and `AvailableBytes` stays 0.

## Expected

The tests use a path under their own temporary directory (absent child of `t.TempDir()`), so no file on the host can change their outcome. Whether `doctorDiskSpaceAncestor` should also walk past `ENOTDIR` (a file where a directory is expected) is a design choice for the Spec.

## Evidence
