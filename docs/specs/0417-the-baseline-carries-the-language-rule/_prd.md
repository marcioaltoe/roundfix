# The Baseline carries the language rule for code, data and products

An Agent in a repository that takes the Baseline reads its guides before it names anything, and those guides say nothing about the language of a name. Their one sentence about names tells the Agent to use the glossary's terms in code, so a repository whose glossary is Portuguese gets Portuguese identifiers. The maintainer decided one rule for every project on 2026-11-20, and it lives in a user-level file that no collaborator, other machine or other harness reads. Six repositories have since written a rule of their own, in six different texts. After this Spec the Baseline states the rule once: English for code and infrastructure, the language each repository declares for what its product's users read, a business term with no faithful translation kept inside an English name, and the glossary as the record of each term's name in code. A repository answers its language once, at its next Baseline update. A codebase whose owner decided that it keeps its language declares that decision with its source. The Pre-PR Review and the QA gate report what breaks the rule, and no existing code is renamed.

## Goals

- An Agent in any repository that takes the Baseline reads, in the guide it already reads first, which language a name takes, which language the product's users read, and what to do with a business term that has no faithful translation.
- A repository's language for its readers is its own answer, given once, and no repository receives one it did not give.
- A business term has one name in code, the one the glossary records, in every later session.
- A new name that breaks the rule and user-facing text in the wrong language are reported where a diff and a product are already read, with no new tool.
- No existing code is renamed, here or in any adopter, and a codebase whose owner decided that it keeps its language declares that decision instead of living beside guides that contradict it.

## User Stories

1. As an Agent about to name a variable, a file, a table or a route, I want the guide I read first to say which language the name takes, so that I do not copy the language of the glossary or of the conversation into the code.
2. As an Agent writing a screen, a message, an e-mail or the description of an MCP tool, I want the guide to name the language this product's users read, so that I write for them and not for the team.
3. As an Agent that meets a fiscal or legal term with no English equivalent, I want one rule for the term and one place that records its name in code, so that I neither invent a translation nor write a name another session will write differently.
4. As the maintainer of an adopter, I want to answer the language of my readers once, at my next Baseline update, so that my guides state my product's answer and not another repository's.
5. As the owner of a codebase written in another language that I decided to keep, I want to declare that decision with its source, so that my guides state the language my code really uses and nobody renames it.
6. As the maintainer who reads a Pre-PR Review, I want a new name that breaks the rule reported as a finding with its line, so that it is corrected before the Pull Request and not found months later.
7. As the person who reads a QA Report, I want text a user reads in the wrong language reported as a finding, so that a product for Brazilian business users does not ship an English sentence, or the reverse.
8. As the maintainer of an adopter whose own rules already state or contradict the rule, I want one message that tells me the answer already given for my repository and the line to look at, so that my update does not wait on a question that was answered.

## Core Features

1. **English for code and infrastructure.** The **Language Rule** is the Baseline rule this Spec adds. Its first clause says that these are written in English: variables, functions, classes, files and folders, code comments, database tables, columns and indexes, buckets, prefixes, environment variables, queues, API routes and technical logs. The clause is mandatory and sits in the guide every Agent already reads first, in every repository that takes the Baseline and declares no exception (the maintainer, 2026-11-20: "Cada repositório declara", whose recorded scope reads "code in English for all").
2. **The Reader Language is each repository's answer.** The **Reader Language** is the language a repository declares for what its product's users read. It is a required decision of the Baseline. The guide names the declared language, and a mandatory clause says what is written in it: screens, user messages, e-mails, PDFs, the product's documentation for its users, and the names, descriptions and parameters of MCP tools. The same clause says what the rule leaves alone: Specs, ADRs, agent guides, commits and Pull Requests keep the language the repository already uses (the maintainer, 2026-11-20, fifth answer: "Não"). An update of a repository that has not answered writes nothing, names the decision and says how to answer it, as every new required decision does. No value is recorded for a repository without its answer or its explicit adoption of a suggested one.
3. **An Untranslated Term keeps its form.** An **Untranslated Term** is a term of the business that has no faithful English translation. A mandatory clause says that it keeps its original form inside an English name: an official acronym stays as it is, another term is written without accents, and the rest of the name is English. Brazilian fiscal and legal terms are the case the clause names, with one example of each form, such as `icms_amount` and `apuracao_summary`.
4. **The glossary records the Name in Code.** The **Name in Code** is the name a term's Glossary Definition records for the term when the name used in code differs from the term: the English translation chosen for it, or the original form kept without accents (the maintainer, 2026-11-20, third answer: "No CONTEXT.md, com o nome no código"). A mandatory clause of the domain guide says so. The glossary is the one the Baseline already defines; no glossary folder or second glossary is added. A term gains its Name in Code when a Spec introduces or touches it; no existing glossary is swept.
5. **The domain clause agrees with the rule.** The domain guide's clause about canonical terms in code names says that a code name uses the Name in Code the glossary records for the term. A glossary written in another language no longer orders identifiers in that language. The clause keeps its identity and its mandatory force.
6. **New names only.** A mandatory clause says that a new name follows the Language Rule, that an existing name changes only when its part of the code is touched, that a large rename takes a Spec of its own, and that nothing is renamed in bulk without a request (the coordinator, 2026-11-27: no batch rename of old code). The clause also names who reports a departure: the Pre-PR Review for a new name and the QA gate for text a user reads.
7. **A codebase that keeps its language declares it.** A **Code Language Exception** is a repository's declaration that an existing codebase keeps its language for code and infrastructure names. It holds two things: the language, and the source of the owner's decision, an ADR or another recorded decision of that repository. The guide of a repository that declares it states the declared language for code in place of the clause of Core Feature 1, cites the source, says that new names follow the language of the existing code, and says that the exception covers the codebase that existed when the owner decided and is no choice for a new one. That guide does not state the Untranslated Term clause or the sentences about renaming touched code. The Reader Language and the Name in Code hold there as everywhere. A declaration without a source is refused and writes nothing: no source, no exception. A repository that declares nothing is under English, and nothing in the Baseline selects another language for code without a cited source.
8. **The Pre-PR Review reports a new name that breaks the rule.** The review prompt tells the reviewer to read the language rule that the repository's agent-instructions guide states and to report a name the candidate adds that breaks it: an identifier, a file or folder, a database name or another kind the rule lists. It is a finding like any other, anchored on a line of the candidate diff with what breaks. A name the candidate did not add is not reported, an Untranslated Term is not a finding, and in a repository whose guide states no language rule the reviewer reports nothing for it. The review's policy, record, output and exit codes do not change.
9. **The QA gate reports text in the wrong language.** The QA gate skill tells the gate to report text a user reads that is written in a language other than the Reader Language the repository's guide names. It applies to every surface with user-facing text that the Spec under the gate declares, and the finding is classified by user impact as every QA finding is. In a repository whose guide names no Reader Language the gate reports nothing for it. Both copies of the skill carry the sentence, and its version rises through the record command.
10. **Every profile carries the rule, and this repository reads what it ships.** The guides that each of the five built-in Baseline Profiles renders hold the clauses of Core Features 1 to 6 and the sentence that names the Reader Language. A repository-owned profile receives them through the modules it composes, and where its profile must list the new decision, the refusal it already receives names the decision and the entry to add. This repository declares English as its Reader Language and no exception. Its guides and Setup Manifest change through the Managed Refresh, the derived Baseline files through the sanctioned regeneration, and each module's version through the record step. None is edited by hand.
11. **An adopter's update accounts every clause it held.** The clauses this Spec rewords keep their ids and their mandatory force, so an adopter's next update records them as it did before, and no clause is left unaccounted. No row the Source Baseline recorded is reworded. After the answer is given, the update changes the agent-instructions guide, the domain guide and the Setup Manifest and no other file, and a second update plans no change.
12. **The decision is recorded where people and Agents look.** A new accepted ADR states the Language Rule, the Reader Language as a decision, the Name in Code, the Code Language Exception with its two conditions, and why the check is the review and the QA gate. Its Knowledge Mark is true, because the Agents of every adopter act on it, so its path joins the Standard Export List. The glossary defines the five terms this Spec adds. The user guide's page about the Baseline and its published Decision Document describe the new decision and the declaration, and the skills that describe the Baseline's decisions and the review prompt say what the product now does. One Task writes the ADR together with the clauses it describes, so the record and the guides never disagree on the default branch.
13. **Adopters are told once.** After the release that carries the rule, each of the eleven repositories that hold a Setup Manifest receives one message. It names the Reader Language the maintainer already gave for the repository, or says that the repository answers when its update asks, and how to answer. Where the repository's own rules repeat or contradict the rule, it names the line. It tells the legacy Quaestor to declare its Code Language Exception with its ADR-0141 as the source, and it tells the repository that uses a profile of its own what its profile must list. It carries no list of what changed in the release. The session that follows the release sends the messages; no Task sends one.

## User Experience

**An adopter's next update.** At session start the Update Check reports the release by its title and a Baseline plan for the repository. The update then stops before it writes anything: it reports that the catalog requires a new decision, names it, and gives the two ways to go on, an answer on the command line or the explicit adoption of the suggested value. The maintainer answers with the language the message named, `pt-BR` for a Gesttione product. The update previews the agent-instructions guide, the domain guide and the Setup Manifest, and applies them on confirmation. From then on the guide's opening lines name the Reader Language beside the repository's Verification commands, and the language clauses follow among the guide's rules.

**A codebase that keeps its language.** The owner answers the Reader Language and, in the same update, declares the Code Language Exception with the language and the source, such as the path of the ADR that records the decision. The guide then reads differently from every other adopter's: it says that code and infrastructure names are written in the declared language as the existing code is, by the cited decision, and that this covers the existing codebase only. A declaration that names a language and no source is refused with a message that says what is missing, and nothing is written.

**A repository that uses a profile of its own.** Its update is refused, as today, with a message that names the decision, the template that renders it and the entry its profile must list. After the maintainer adds the entry and answers, the update proceeds as above.

**An Agent at work.** It reads the guide, writes `apuracao_summary` for a summary of an Apuração, and finds in the glossary that Filial is `branch` in code. When it introduces a term whose name in code differs from the term, the Spec's glossary Task records the name with the definition.

**A review.** The Pre-PR Review of a candidate that adds a file named in another language returns a finding anchored on that file's line in the diff, saying that the name breaks the repository's language rule and what the rule asks. A candidate that only touches lines near an old name in another language gets no finding for the old name.

**A QA gate.** The gate that exercises a product whose Reader Language is `pt-BR` and meets an English error message on a screen records it as a finding with the surface, the text and the expected language, and classifies it by what the user loses.

**Empty and error states.** A repository whose guides predate the rule sees no language finding in a review or a QA Report. An update given an answer for a decision the catalog does not have is refused as today.

- A deterministic check of names: a linter, a dictionary or a command that fails a delivery. The maintainer chose the review and the QA gate with no new tool (the maintainer, 2026-11-20, fourth answer: "Review e QA"), and no ready tool holds names to a glossary that maps a term to its name in code (measured by the author).

- A glossary starter file, a `docs/glossary` folder, or a change to the glossary's entry format in the Vendored Skill that owns it.
- A sweep that adds a Name in Code to the terms an existing glossary already holds, this repository's glossary included.
- A Code Language Exception without a cited source, an exception for one part of a codebase, and an exception as a way to start a new codebase in another language.
- Translating Roundfix's own output or documentation. Roundfix declares English, and its readers read English.

## Risks

1. **Every adopter's next update stops once.** A required decision is paid on the next update by each of the eleven repositories, and a repository-owned profile must also list it. Two open Backlog Entries already give adopters a reason to hold an update: the release plan's Baseline check refuses a source above 2 MB, and the update empties an ADR header field in one adopter. The rule reaches a repository only when it updates.
2. **The decision reaches many test fixtures.** In the author's prototype 188 tests of one package failed until their fixtures gained the new answer, and the answers of the required decisions are listed in twelve test files, eight parity fixtures and five plan goldens across two packages, four of those test files governed. The work is mechanical and wide, and the coverage record changes with every test added.
3. **The canonical-terms clause is pinned to its old words in three places.** One governed test holds it to the text the Source Baseline recorded, and two fixtures quote it. Rewording it changes all three, and the TechSpec chooses between that and stating the Name in Code beside it.
4. **A new clause inside a rule the Standard TypeScript profile requires needs a Source Baseline row.** The prototype's catalog refused five such clauses. A new rule outside the required rules loaded without one. The TechSpec chooses, and the choice moves five governed files in or out of the grant.
5. **A reviewer and a QA gate are weak judges of language.** Both are models reading text, a published study found that code generated from a non-English prompt mixes languages, and a false finding costs a review round. The instruction is bounded to names the candidate adds and to text a user reads, and the first Specs under the rule give the numbers that would justify a deterministic check.
6. **The review prompt grows for every review of every repository,** the ones without the rule included. The instruction is one sentence and reports nothing where the guide states no rule.
7. **The guides grow.** They hold 96,009 bytes today and every Authoring Phase reads them. The trial wording added 1,326 bytes without the sentence that names the Reader Language. The text of the exception renders only where it is declared.
8. **The Vendored Skill that owns the glossary's format says the glossary holds no implementation detail.** A Name in Code is one such line, decided by the maintainer. Until the catalog's text agrees, an Agent reads a mandatory clause and a skill sentence that pull apart; the clause is the rule (`## Open Questions`, item 4).
9. **The exception can be misused.** Only the cited source holds it. A citation of a decision that does not say what the declaration claims is the owner's error, and no check of this repository can read another repository's ADR.
10. **Some names are on neither list:** the keys of an MCP response, a command-line flag, an error message to an operator. The clauses name the kinds the maintainer listed, and a repository that needs more decides it in its own rules, as one adopter already did.
11. **The coordinator decided the exception on the maintainer's earlier decision.** The maintainer confirmed it on 2026-11-27 (`## Decisions`), so the plan keeps it; the risk that remains is the misuse item 9 names.
12. **The gates must fit their numbers.** The new tests are in-process catalog, prompt and document tests. This Spec asks for no Measured Dossier, so the work fits the numbers the Gate Time Rule holds.
