# Verification cost — measured result, 2026-08-03

Same machine, same commands as `2026-08-02-before.md`. macOS, 12 cores.

The before-figures are quoted from that frozen file and were not re-derived:
comparing against a re-measured "before" would make the comparison circular.

## Headline

| Measurement | Before | After | Delta |
| --- | --- | --- | --- |
| `go test ./... -count=1`, warm build cache | 136.9s | **88.9s** | **−35%** |
| `go test ./... -count=1`, cold build cache | 146.2s | **94.1s** | **−36%** |
| `make verify`, unchanged tree | 142.2s | **4.9s** | **−97%** |
| `make verify`, after an edit to a light package | 142.2s | **~5s** | **−96%** |
| `make verify`, after an edit to `internal/cli` | 142.2s | **48.5s** | **−66%** |
| `make verify`, after an edit to `internal/baseline` | 142.2s | **54.5s** | **−62%** |

Two different numbers matter, and conflating them is how the original Spec got
its premise wrong.

**The gate's own cost** is the first two rows: what CI pays to judge the whole
tree from nothing. That fell 35%.

**The implementation loop's cost** is the last three: what a maintainer pays
between edits. That fell 97% in the common case, and it is the number the
maintainer's constraint was actually about.

## What actually produced the win

**Not what the Spec predicted.** It assumed sequential execution was the cost
and cold compilation a large secondary one. Both were wrong:

- Cold versus warm was 9.3s on the full suite, never the 148s an earlier
  finding suggested. That older figure was Go's *test-result* cache, which
  `-count=1` disables by design.
- The eight heaviest end-to-end journeys complete in 31.7s together — a 6.9×
  compression against their serial sum. They were never the bottleneck.
- Raising `-parallel` from 4 to 20 left the suite flat at 140–145s, so
  scheduler contention was not the constraint either.

**The prefactor was the whole game, and it was not optional.** Go refuses
`t.Parallel()` in any test that calls `t.Setenv` or `t.Chdir`, because both
mutate state the entire process shares. Removing that dependency — making code
take its working directory and environment as arguments (ADR-0089) — is what
made 479 of 488 declarations legal. Tasks 02 and 04 changed no test timing on
their own; they removed the reason the timing could not change.

**Measured mid-flight, the work was going the wrong way.** After tasks 02–05
the suite had gone from 136.9s to 168.5s and `internal/cli` was 27% *worse*.
Only 207 of 488 tests declared parallelism, and of the 281 still sequential
just nine had a real blocker. That measurement is what produced task_08, and
task_08 is what produced the headline.

**The cache turned out to be the real lever for the loop.** Removing every
`t.Setenv` and `t.Chdir` did something the Spec never set out to do: it made
Go's test-result cache trustworthy. A test that mutates process state can pass
or fail on something the cache cannot see; a test that takes its environment
as an argument cannot. So the local gate can now let the cache decide what to
re-run, and a second `make verify` costs 4.9s instead of 142.2s.

## How the two tiers divide

Go's test cache keys on the compiled test binary and on the files and
environment each test read. A change that never reaches the test binary — a
comment, an unreferenced function the linker drops — leaves it byte-identical,
and the cached verdict stays valid because the binary that produced it is the
binary that would run. This was verified directly: adding an exported function
to `internal/cli/cli.go`, and adding an unused helper to `cli_test.go`, both
left the package `(cached)`; adding a real `func Test…` re-ran it in full. A
change that does reach the binary re-runs that package, and only that package.

So the local gate runs **every test** and pays for **what changed**:

| Local edit | `make verify` |
| --- | --- |
| nothing, or nothing that reaches a test binary | **4.9s** |
| any of the 20 light packages | **~5s** |
| `internal/cli` | **48.5s** |
| `internal/baseline` | **54.5s** |

CI is the tier that owes a verdict on the whole tree regardless of what any
cache believes, so `.github/workflows/ci-verify.yml` sets `GOFLAGS: -count=1`
and every package executes: **88.9s**, plus the race detector.

No test was deleted, skipped, or moved out of the local gate. The tier boundary
is the cache, not a test list.

## What forcing a fresh run found

Running the full suite three times with `-count=1` surfaced a flake the cached
gate had been hiding: `TestRunResolveDetachedChildReportsProfileProofFailure`
failed once with `TempDir RemoveAll cleanup: directory not empty`. It is the
only test that drives the detached-child branch, and that branch mutates
process-global state — the test hands production code a raw file descriptor
number, and `newDetachChildFromEnv` calls `os.Unsetenv` twice. Go refuses
`t.Parallel()` next to `t.Setenv` for exactly this reason, but cannot see the
mutation when it lives in production code, so the hazard ran unguarded. The
test is now sequential with that reason stated inline; three consecutive fresh
runs then passed at 89.3s, 87.9s, and 88.9s.

A second, different failure appeared when an extra parallel test was injected
to force cache invalidation: `TestRunImplementQueuedCancellation…` reported
`timed out waiting for 2 Agent starts`. That family of tests orchestrates real
child processes and asserts concurrency semantics, so it needs CPU to make
progress — and it now runs beside hundreds of parallel siblings. Its waits were
budgeted at 10 and 20 seconds, which under a saturated machine measures load
rather than correctness. They now share one named `implementWaitBudget` of 90
seconds, deliberately far longer than the work needs: a passing wait returns
the moment its condition holds and pays none of it, while a stuck one still
fails. The passing path is unchanged at 47.4s, and three *concurrent*
full-package runs — roughly 2.6× oversubscription — all passed at 114–124s.

Both defects were latent before this Spec. Sequential execution hid them; it did
not prevent them.

That is the argument for the CI tier existing at all. Until this Spec, nothing
ran the suite before a merge — only the release workflow, on a tag push.

## Where the remaining time is

`internal/baseline` at 50.1s is now the floor, and it is already at 188
parallel declarations against 176 test functions, so declaring more will not
help. Its cost is the work each test does, not how the tests are scheduled.
That is a different Spec.

## Reproducing

```bash
go test ./... -count=1                          # 88.9s
GOCACHE=$(mktemp -d) go test ./... -count=1     # 94.1s
for p in $(go list ./...); do go test "$p" -count=1; done
make verify                                     # 4.9s on an unchanged tree

grep -rc 't.Parallel()' internal/cli internal/baseline
grep -rc '^func Test' internal/cli internal/baseline
```
