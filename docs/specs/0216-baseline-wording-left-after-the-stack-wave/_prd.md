# Baseline wording left after the stack wave

The stack wave (Specs 0206 to 0208) gave the Baseline's stack rules force but
left sentences that are untrue for some repository that reads them. The
backend and frontend guides say "the workspace" without naming it, although
the built-in profiles declare its path. The clause that forbids generic
`modules` or `services` buckets has no scope, so it reads as a ban on domain
services. Nine dispatch triggers name a skill that only a person can start, so
an Agent is told to activate something it cannot load. This refactor makes the
three sentences true, records who owns the production-code and debugging
activations, and states with evidence which items of the adopted entries were
already settled on main. It changes Baseline assets, one render token and their
tests; no command, flag or recorded decision changes.

## Goals

- A Standard TypeScript Monorepo or composed-profile adopter reads the path of
  its backend and frontend workspaces in the guides that govern them; a
  repository whose profile declares no workspace reads the same bytes as
  today.
- The backend bucket clause forbids generic buckets in place of the layers,
  says that a domain service in the domain layer is not one, and reaches a
  Source Baseline adopter as a declared replacement of the clause it holds.
- Every adopter's skill guide tells the Agent to ask the person to run a
  matching skill that only a person can start.
- The owner of the production-code and debugging activations is recorded with
  the rule that forces it.

## Core Features

1. **Scoped bucket clause.** `clause.backend.prohibit-generic-buckets`
   (prohibited) replaces `clause.backend.prohibit-generic-layers`, declares
   the replacement, and gains its Source Baseline row. The old row stays as
   the record of what adopters hold.
2. **Declared workspace paths.** Each workspace entry of the two built-in
   TypeScript profiles names its guide, and the backend and frontend scope
   sentences render the bound path through a new `workspace.location` token.
   A guide with no bound workspace renders the token empty.
3. **Person-only skills.** A new core clause,
   `clause.core.ask-the-person-to-start-a-person-only-skill` (mandatory), in
   the skill guide of every profile, with its Source Baseline row.
4. **Activation owner recorded.** ADR-0222 records why `typescript` owns
   `trigger.production-code` and `trigger.debugging`; no catalog change.

## Already settled on main

Re-measured on `6364d3c9`, which includes Specs 0206 to 0209 and 0213:

- **The TypeScript setup's "unused" skills.** `zustand`, `motion` and
  `tanstack-table` are required and dispatched by the `frontend` module, and
  `ai-sdk` by the `backend` module (`trigger.frontend.zustand`,
  `trigger.frontend.motion`, `trigger.frontend.tanstack-table`,
  `trigger.backend.ai-sdk`), and all four appear in the Standard TypeScript
  Monorepo golden skill guide. Every TypeScript profile selects both modules.
  Nothing to change.
- **The backend guide's fixed auth owner.** The Better Auth section renders
  only from the recorded `auth.provider` decision, which applies only when the
  profile requires `capability.stack.better-auth`. oraculum, whose
  repository-owned profile selects the backend module without Better Auth,
  renders no auth section in its backend guide. The owner name equals the only
  provider the decision accepts. Nothing to change in the backend guide; the
  dispatch residue is recorded under Recorded limits.

## Non-Goals / Out of Scope

- Rewording the production-code and debugging triggers, or moving them to
  another module (see ADR-0222).
- Any change to `auth.provider`, its rendering, or the per-technology triggers
  a repository-owned profile receives.
- Letting a repository-owned profile declare workspaces, or checking that a
  declared workspace exists on disk.
- Marking person-only skills in the catalog, or removing their triggers.
- Editing any skill, vendored or owned, or any setup snapshot.
- Any Makefile, lint, formatter, CI or `go.mod` change.

## Recorded limits

- The person-only clause relies on the Agent seeing that a skill cannot be
  activated; no check reads an installed skill's metadata.
- A repository-owned profile renders every per-technology trigger its modules
  carry: oraculum's skill guide dispatches `better-auth` and `ai-sdk`
  although its backend uses neither. Gating a trigger on a capability needs a
  catalog field that does not exist and is left for a later Spec.
- No check reads an adopter's directories; a declared workspace path is what
  the profile says, not what the disk holds.

## Decisions

- **Grouping.** The two adopted Backlog Entries change the same skill guide
  and stack guides, so they share one Spec within three implementation Tasks
  and a QA gate.
- **Ask, don't hide.** A person-only skill keeps its trigger and the Agent
  asks the person. See ADR-0222.
- **Owner by setup.** `typescript` keeps the production-code and debugging
  activations. See ADR-0222.
