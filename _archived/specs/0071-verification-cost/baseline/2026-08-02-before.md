# Verification cost — measured baseline, 2026-08-02

Captured on `main` at `467dd6a` before any change from this Spec, so the
"after" has something to be compared against. macOS, 12 cores, moderate load,
no competing build.

Every figure uses `-count=1`, which disables Go's test-result cache. That is
what the Daemon runs, so it is what the baseline must measure.

`internal/baseline` has 41 tests that already isolate their filesystem with

`TestMain` and `sync.Once`, so repeated compilation is not a cost there.

## What the numbers say

**Compilation is not the problem.** Cold versus warm is 9.3s on the full
suite. An earlier finding recorded 148s cold against 5s warm for `make verify`,
but that 5s was Go's *test-result* cache returning cached passes — which
`-count=1` disables by design. Warming the build cache is worth about nine
seconds, not two minutes.

**Packages already run in parallel.** The sum of per-package times is ~234s
while the full suite is 136.9s, so `go test ./...` is already overlapping
packages.

**The floor is the slowest package.** Because packages overlap, the suite can
never finish faster than `internal/cli` alone, which is 113.2s of essentially
sequential work — 488 test functions and one `t.Parallel()` call on a
twelve-core machine. Any improvement that does not touch `internal/cli` cannot
move the suite below ~113s.

**Two packages are 84% of the cost.** Everything outside `internal/cli` and
`internal/baseline` sums to about 37s, and the fifteen smallest packages to
about 8s combined. Effort spent anywhere else is noise.

## Reproducing

```bash
# full suite, warm
go test ./... -count=1

# full suite, cold
GOCACHE=$(mktemp -d) go test ./... -count=1

# per package
for p in $(go list ./...); do go test "$p" -count=1; done

# parallelism census
grep -rc 't.Parallel()' internal/cli internal/baseline
grep -rc '^func Test' internal/cli internal/baseline
```

The "after" run must use the same commands on the same machine, and record
both the headline table and the per-package table.
