# Run Event Journal baseline — 2026-08-11

Measured production commit: `685d201b658cc46e944634a3c072da2a7d1d83c3`
(`docs: make every 0081 verification able to fail before its work`). The
measurement harness and this report are Task 01 additions; no production file
differed from that commit while the baseline ran.

The baseline isolates two costs. Concurrent writers increased event-write tail
latency and the lock-wait estimate, while the current 30-second SQLite timeout
kept `SQLITE_BUSY` at zero in all 336 attempts across two runs. The Run-start
retention path scaled with journal size: p50 was 0.062–0.069 ms with an empty
journal, 1.128–1.146 ms at 1,000 events, and 11.449–11.551 ms at 10,000 events.

## Harness and parameters

Rerun the same two-sample measurement from the repository root:

```sh
rtk proxy go test -count=2 ./internal/store -run '^TestJournalMeasurementHarness$' -v
```

The harness lives in `internal/store/journal_baseline_test.go` and uses these
fixed parameters:

| Parameter | Value |
| --- | ---: |
| Seeded journal sizes | 0, 1,000, 10,000 events |
| Concurrent writer counts | 1, 2, 4 |
| Writes per writer | 8 |
| Payload size | 1,800 bytes of raw JSON |
| Run-start samples per journal size | 5 |
| SQLite `busy_timeout` | 30,000 ms |

Each matrix row and each Run-start size gets a new `t.TempDir()` Roundfix Home
and a newly migrated Run Database. The harness creates and seeds its own Run;
it never resolves or opens the operator's Roundfix Home. The seeded Run is
terminal but completed one hour after the retention cutoff, so the eligibility
query must aggregate its journal but must not prune it.

Event-write latency is wall time around the production `AppendRunEvent` call.
Each writer owns an independent Store connection to the same fixture, and all
writers start each of eight rounds together. `SQLITE_BUSY` is counted from the
SQLite driver's typed result code. Other errors fail the harness.

The lock-wait metric is the concurrency-attributable delay for each successful
write: `max(0, write latency - same-size one-writer p50)`. It is an external
estimate because the production append path exposes no lock-acquisition hook;
it includes SQLite writer waiting and scheduler queueing. Keeping this
definition in the harness makes before/after comparisons use the same
measurement boundary without adding a production-only test hook.

The Run-start measurement reproduces the no-candidate retention sequence used
at operational preflight: `TerminalRunPruneCandidates` followed by
`PruneTerminalRuns`. The second call takes the immediate write transaction and
repeats the current full-journal aggregate. The reported database bytes are
`PRAGMA page_count * PRAGMA page_size` after seeding.

## Run-start retention results

All durations are microseconds.

| Journal events | Database bytes | Samples | Run A p50 | Run A p95 | Run B p50 | Run B p95 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 0 | 61,440 | 5 | 62 | 123 | 69 | 106 |
| 1,000 | 2,162,688 | 5 | 1,128 | 1,220 | 1,146 | 1,242 |
| 10,000 | 21,135,360 | 5 | 11,449 | 11,899 | 11,551 | 11,845 |

At 1,000 and 10,000 events, Run-start p50 differed by 1.6% and 0.9% between
runs. Increasing the fixture from 1,000 to 10,000 events increased p50 by
roughly tenfold in both samples. This is the baseline evidence that the current
retention eligibility path is journal-size-dependent.

## Limits

- The largest fixture is 10,000 events, not the observed 1.6-million-event
  operator database. The harness establishes the cost curve without copying or
  reading live data; it does not justify extrapolating an exact fleet latency.
- `SQLITE_BUSY = 0` is the observed result under the current 30-second timeout,
  not proof that the writers avoid contention. The lock-wait and tail-latency
  columns expose contention that the timeout masks.
- The lock-wait value is a stable before/after estimate, not direct SQLite
  instrumentation. Scheduler load can move it, which is why comparisons must
  preserve the machine, parameters, and synchronized-writer scenario.
