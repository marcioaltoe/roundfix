## Static gate

`rtk make verify` ran without a pipe and exited 2 in its first executed stage:

```text
rtk go test -parallel 16 ./...
Go test: 3197 passed, 1 failed, 3 skipped in 25 packages
store (174 passed, 1 failed)
[FAIL] TestOwnerProcessControllerForceKillExitProof
process_unix_test.go:57: owner process helper did not become ready:
read |0: file already closed
make: *** [test] Error 1
```

The failure is code-caused. A compiled direct invocation of the helper with
`ROUNDFIX_OWNER_PROCESS_HELPER=ignore` deterministically printed `ready`, then
exited 2 with `fatal error: all goroutines are asleep - deadlock!` at
`internal/store/process_unix_test.go:473`. The helper's ignore branch calls
`select {}`, so it does not stay alive for the parent to exercise. The parent
also starts `cmd.Wait` before its scanner drains `StdoutPipe`; when the child
exits immediately, that race can close the pipe before the scanner reads the
readiness line, producing the gate's exact `file already closed` failure.

A 50-run focused parent command exited 0, but every child printed the same
fatal deadlock. That proves a passing focused status does not establish the
journey: the parent often reads `ready` before the broken child exits. The
store test files are unchanged between `origin/main` and this build, but a
pre-existing code defect is still code-caused rather than an environment
block. Per the gate contract, public flow QA stopped after this static failure;
the later `spec-budget`, skill, build, and `spec-check` stages did not run.

## Findings

### F-002 — Store process helper exits with a runtime deadlock before the test controls it

- Impact: Blocks-Completion.
- Actor and journey: contributor running Q-15 through the repository's
  mandatory `make verify` entry point.
- Expected: `TestOwnerProcessControllerForceKillExitProof` starts an
  ignore-mode owner process, observes its readiness, force-kills it, and the
  full gate continues through the dedicated budget, build, and Spec-check
  stages with exit 0.
- Actual: the full gate exits 2 because the readiness scanner receives
  `read |0: file already closed`. A direct helper invocation prints `ready`,
  then exits 2 with a runtime deadlock at
  `internal/store/process_unix_test.go:473`. The parent starts `cmd.Wait` at
  line 493 before scanning the stdout pipe at line 505, so the premature exit
  can close that pipe before readiness is consumed.
- Reproduction:
  1. Run `rtk make verify`; observe exit 2 at
     `TestOwnerProcessControllerForceKillExitProof` with `file already closed`.
  2. Build the package test binary with
     `rtk proxy env GOCACHE=/Users/marcio/.roundfix/worktrees/roundfix-339f8dac/run_20260804T144138Z_ee144d7fb80429b3/.gocache GOFLAGS=-buildvcs=false go test -c -o /private/tmp/roundfix-0064-store.test ./internal/store`.
  3. Run
     `rtk proxy env ROUNDFIX_OWNER_PROCESS_HELPER=ignore /private/tmp/roundfix-0064-store.test -test.run='^TestOwnerProcessHelper$' -test.v`;
     observe `ready`, then exit 2 and `fatal error: all goroutines are asleep - deadlock!`.
  4. Run the focused parent/helper pair with `-count=50`; observe exit 0 even
     though every child emits the fatal deadlock, proving the focused parent
     result can pass for the wrong reason.
- Evidence: Static gate; Evidence README E-15.
- Affected rows: Q-02 through Q-15.
- Unblocking requirement: make the ignore-mode helper remain alive until the
  controller kills it, coordinate pipe consumption and `Wait` without the
  close/read race, add a regression that rejects premature helper exit, then
  rerun `make verify` and the full public-flow matrix. Retrying the gate or
  suppressing the child stderr would only hide the defect.
